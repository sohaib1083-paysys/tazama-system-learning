# 5.1 — Where ML fits in a system like Tazama

You're into AI, so let's place it properly. The mistake beginners make is
thinking "add AI" is a feature you sprinkle on. In real systems, ML is **a
component with the same system-design constraints as any other** — latency,
failure, state, deployment — plus a few of its own. The Tazama ecosystem
actually has several ML pieces, so we'll ground it.

## Rules vs ML: two ways to make a decision

Tazama's core is **rule-based** ([2.4](../02-tazama-architecture/2.4-rules-typologies-scoring.md)):
humans write explicit logic ("amount > 3σ above this customer's mean → flag").
ML is the **other** approach: instead of writing the logic, you show a model many
labeled examples ("these 100k transactions were fraud, these 5M weren't") and it
**learns** a function that predicts fraud. Understanding when to use which is a
senior judgment:

| | **Rules** (Tazama's core) | **ML models** |
|---|---|---|
| How logic is created | Humans write it | Learned from data |
| Explainability | High — you can read the rule | Often low ("why did it flag this?") |
| Handles novel patterns | Only what you anticipated | Can catch unanticipated patterns |
| Needs labeled data | No | Yes, lots |
| Regulatory comfort | High (auditable) | Harder (must explain decisions) |
| Changes | Edit config/rule | Retrain + redeploy model |

In fraud/AML, **explainability is often legally required** — you may have to
justify why you blocked someone's money. That's a big reason Tazama's *core
decisioning* is rule-based and auditable. **ML tends to appear at the edges**:
prioritization, triage, enrichment, analytics — places where a wrong answer is
advisory, not a blocked transaction. Watch for that pattern; it's a mature way to
adopt ML: *let ML advise, let auditable logic decide.*

## The ML pieces actually in the Tazama ecosystem

You have real examples on disk — let's map them to where they sit:

### 1. `ATM-AI-API` — a model served behind an HTTP API

`/home/sohaib/Documents/frms/ATM-AI-API` is a **FastAPI** (Python) service that
serves a trained **stacking ensemble** (Random Forest + Gradient Boosting +
AdaBoost) to predict ATM transaction **priority** with a **confidence score**.
Its shape is the canonical "model in production" pattern:

```
POST /predict   { "features": [1200, 0.1, 0.3, ... 34 numbers] }
  → { "prediction": ..., "confidence": ... }
GET  /health    → is the model loaded and ready?
GET  /model-info → what model, what version?
```

Look at what makes this a *system component*, not a notebook:
- It's **HTTP request/response** ([3.1](../03-messaging-and-data/3.1-messaging-models.md)) —
  a caller sends features, gets a prediction *now*. (Contrast Tazama's core,
  which is async/NATS. A model scoring one input is naturally synchronous.)
- It has a **`/health`** endpoint — so a load balancer / K8s can know if it's
  ready ([1.5](../01-foundations/1.5-design-for-failure.md), [4.3](../04-devops-networking/4.3-kubernetes-from-first-principles.md)).
- It's **dockerized** (there's a `Dockerfile` + `docker-compose.yml`) — so it
  deploys like every other service. **A served model is just another container
  with an API.** That realization removes most of the mystery.
- It returns a **confidence score**, not just a label — mature ML systems expose
  uncertainty so downstream logic can treat low-confidence predictions
  differently (e.g., send to a human).

### 2. `data_collection` — the training side

`/home/sohaib/Documents/frms/data_collection` has `fraud_detection_ML.ipynb`, a
`ml_training_dataset.csv`, and a `fraud_detection_api`. This is the **other half**
of ML: **training**. A notebook explores data and trains a model; the dataset is
the labeled examples; the API serves the result. Notice the two-world split:
**training** (offline, notebook, big data, slow, iterative) vs **serving**
(online, API, one input, fast). Keeping these straight is fundamental — it's the
subject of [5.2](5.2-serving-and-mlops.md).

### 3. CMS **AI triage** — ML assisting humans

The Case Management System has a **triage** module
(`case-management-system/backend/src/modules/triage/`) with **AI-assisted**
triage. This is ML in its ideal fraud role: when an alert becomes a case, AI can
**suggest** a priority or summary to help the investigator — but a human still
decides. ML *assists*, auditable process *governs*. Again: advise, don't
auto-decide the money.

### 4. `biar` — the analytics/lakehouse + JupyterHub

`/home/sohaib/Documents/frms/biar` is a **data lakehouse** (PySpark, Apache Hudi,
NiFi, JupyterHub with fraud analytics dashboards). This is the **data platform**
that feeds ML: it ingests, transforms (ETL), and stores large volumes so analysts
and models can learn from history. Every serious ML effort needs this "where does
the training data come from and how is it prepared?" layer — and here it is, a
whole subsystem.

## The mental model: ML is a pipeline, and each stage is a system

```
  DATA          →  FEATURES     →  TRAIN        →  SERVE         →  MONITOR
  (biar/          (turn raw        (notebook,      (ATM-AI-API,     (is it still
   data_collection data into        offline)        FastAPI +        accurate?
   lakehouse)      model inputs)                     confidence)      drift?)
```

Notice: only the **SERVE** box is in the request path at 3,000 tx/s; everything
else is offline. So the system-design constraints differ per stage — training can
be slow and batchy; serving must be fast and reliable like any other API. **Don't
apply "must be real-time" to the whole ML pipeline — only to serving.**

## The senior framing

When someone says "let's add AI," the senior questions are:

1. **Does a rule already do this well?** (If yes, ML adds cost and opacity for
   little gain — Tazama's core stays rules for good reason.)
2. **Do we have labeled data?** (No labels → no supervised ML. This is usually
   the real blocker.)
3. **What happens when the model is wrong?** (If a wrong answer blocks money →
   ML must not decide alone. If it just reorders a work queue → fine.)
4. **How will we know when it silently degrades?** (Models rot as the world
   changes — [5.2](5.2-serving-and-mlops.md).)
5. **Can we explain a decision if a regulator asks?**

Those five questions are worth more than any model architecture. ML is a tool
with a *system* around it — and you already understand systems.
