# 5.2 — Serving models, features & the MLOps loop

This lesson is about running ML *in production reliably* — the part that's 90% of
the real work and 10% of the hype. It's mostly systems engineering, which you now
have.

## The two worlds: training vs serving

Internalize this split; almost every ML production bug lives in the gap between
them.

| | **Training (offline)** | **Serving (online)** |
|---|---|---|
| When | Occasionally (retrain) | Every request |
| Latency | Hours/days OK | Milliseconds |
| Data | The whole history, in batch | One input at a time |
| Environment | Notebook / Spark cluster | An API service (e.g. FastAPI) |
| In Tazama | `data_collection` notebook, `biar` lakehouse | `ATM-AI-API` |
| Failure impact | A worse *next* model | A *live* request fails |

The model is trained in world 1 and **shipped as an artifact** (a file — weights)
into world 2, where it's loaded and served. `ATM-AI-API` loads a pre-trained
stacking ensemble at startup and serves it — that's the handoff between the two
worlds.

---

## The feature problem (the #1 subtle ML systems bug)

A model doesn't eat raw transactions; it eats **features** — engineered numbers
(you saw `ATM-AI-API` takes a 34-number feature vector). Here's the trap:

> The features you compute **at training time** must be computed **identically at
> serving time.** If training used "average transaction amount over 30 days" but
> serving computes it slightly differently, the model gets inputs it never
> trained on and quietly makes bad predictions. This is **training/serving
> skew**, and it's the most common serious ML production bug.

The system-design answer is a **feature pipeline** shared (or carefully mirrored)
between training and serving — often a **feature store**. The lesson for you:
*features are a system-integration problem, not a modeling problem.* Where does
`ATM-AI-API`'s 34 features come from, and are they built the same way as in the
training notebook? That question is exactly the senior concern.

## Serving a model = a normal service (you already know this)

Once trained, serving is *just a service* with the properties from Modules 1–4:

- It's an **API** (`/predict`) — request/response ([3.1](../03-messaging-and-data/3.1-messaging-models.md)).
- It has a **`/health`** check so orchestration knows it's ready ([4.3](../04-devops-networking/4.3-kubernetes-from-first-principles.md)) —
  note ML health means *"is the model loaded?"*, not just "is the process up."
- It's **containerized** and deployed like anything else ([4.2](../04-devops-networking/4.2-containers-and-docker.md)).
- It should be **stateless** (the model weights are loaded read-only; each
  request is independent) → it **scales horizontally** ([1.4](../01-foundations/1.4-state-the-hard-problem.md))
  just like a rule-executer. Run 10 copies behind a load balancer.
- It needs **timeouts** and **fallbacks** ([1.5](../01-foundations/1.5-design-for-failure.md)):
  what does the caller do if the model service is slow or down? A mature design
  has a fallback (e.g., default priority) rather than blocking. Returning a
  **confidence score** enables another fallback: "if confidence < threshold,
  route to a human."

So "deploy an ML model" is not a new skill — it's **the systems skills you have,
applied to a service whose logic happens to be learned.** That's the confidence I
want you to leave this lesson with.

## MLOps: the loop that keeps a model honest

Software you deploy stays correct until you change it. **A model deployed
unchanged silently gets *worse* over time**, because the world changes — new
fraud patterns emerge, customer behavior shifts. This is **model drift**. So ML
needs an ongoing loop, **MLOps** (DevOps for ML):

```
   ┌──────────────────────────────────────────────────────────┐
   │                                                          ▼
 TRAIN ──▶ VALIDATE ──▶ DEPLOY ──▶ SERVE ──▶ MONITOR ──▶ (drift?) 
   ▲                                              │
   └──────────────── retrain on fresh data ◀──────┘
```

Each stage maps to things you already know:

- **Version everything** — not just code, but the **model artifact** and the
  **dataset** it was trained on. (`ATM-AI-API` exposing `/model-info` is the seed
  of this — you must know *which* model is live.) Reproducibility = versioned
  code + data + weights.
- **Validate before deploy** — like tests for code, but "is the new model
  actually better on held-out data?" Don't ship a worse model.
- **Deploy safely** — canary/gradual rollout, and **rollback** if the new model
  misbehaves (same as `helm rollback`, [4.4](../04-devops-networking/4.4-helm.md)).
  Often run the new model in **shadow mode** first: it predicts but its output
  isn't used, so you compare it to the live one on real traffic risk-free.
- **Monitor** — track prediction distributions and accuracy over time. If inputs
  or outputs drift from training, **alert** (Module 6.2). This is observability
  applied to ML.
- **Retrain** — on fresh, newly-labeled data, and loop.

The `biar` lakehouse + `data_collection` datasets are the "fresh data" and
retraining substrate; a served API like `ATM-AI-API` is the "serve" box. You can
see the makings of the whole loop across the ecosystem.

## LLMs / generative AI (a note, since you're into AI)

Everything above applies to classic ML (the stacking ensemble). **LLMs** (like
the AI-triage assist in the CMS) add their own systems concerns, all familiar:

- They're usually **called over an API** (request/response) — often a *slow*
  dependency (seconds), so **timeouts, async handling, and fallbacks** matter
  even more ([1.5](../01-foundations/1.5-design-for-failure.md)).
- They're **non-deterministic** — the same input can give different outputs. That
  complicates testing and idempotency ([1.4](../01-foundations/1.4-state-the-hard-problem.md)).
- They can **hallucinate** — so in a regulated fraud context, an LLM **assists**
  (drafts a case summary, suggests a triage priority) and a human/rule
  **governs**. Same principle as [5.1](5.1-ml-in-systems.md): *advise, don't
  auto-decide the money.*
- **Cost & rate limits** are real system constraints — you cache, batch, and
  guard them like any expensive dependency ([3.4](../03-messaging-and-data/3.4-caching-and-redis.md)).

The pattern holds: an LLM is a *slow, non-deterministic, expensive service*, and
you already know how to design around slow/expensive/failing services.
