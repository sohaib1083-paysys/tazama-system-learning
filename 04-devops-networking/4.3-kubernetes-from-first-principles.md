# 4.3: Kubernetes from first principles

Docker Compose runs many containers on **one machine**. But production runs on
**many machines**, machines die, traffic spikes, and you need it to heal itself.
**Kubernetes (K8s)** is the system that runs containers across a fleet of
machines and keeps them running the way you asked. This lesson builds it up from
the one core idea, then names each piece using Tazama's real Helm-chart manifests.

## The one idea: declarative desired state

This is the whole philosophy, and once it clicks, K8s stops being scary:

> **You don't tell Kubernetes *what to do*. You tell it *what you want to be
> true*, and it continuously works to make reality match.**

You declare "I want 3 copies of the rule-executer running." K8s constantly
checks: are there 3? One crashed → it starts another. A machine died → it
reschedules those copies elsewhere. You never run "start a container" commands;
you edit the **desired state** and K8s **reconciles** reality to it. This
**control loop** (observe → compare to desired → act) is the heart of everything
in K8s.

Compare: Docker Compose is imperative-ish ("bring these up"). K8s is
**declarative** ("this is how the world should look, keep it that way"). That
declarative + self-healing nature is why it runs serious systems.

## The building blocks (each is just a YAML object you declare)

Let's build from smallest to largest, with Tazama's actual manifest files.

### Pod — the smallest unit

A **Pod** is one (or a few tightly-coupled) containers that run together, share a
network address, and live/die together. **You rarely create Pods directly** —
they're what higher-level objects manage. Think of a Pod as "one running instance
of your service." Remember Tazama's **sidecar** logging pattern
([3.2](../03-messaging-and-data/3.2-nats-deep-dive.md))? A processor + its logging
sidecar in one Pod is *exactly* the multi-container-Pod use case.

### Deployment — "keep N stateless copies running"

A **Deployment** says "run N identical Pods of this image, and if any die,
replace them; when I update the image, roll it out gradually." This is the
workhorse for **stateless** services (Module 1.4 — the ones you can freely copy).

Real Tazama Deployment (`FST-performance/tazama-lf/EKS-helm/charts/arangodb-single/templates/deployment.yaml`),
simplified — read the annotations:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: arango, namespace: development }
spec:
  replicas: {{ .Values.arangodb.replicas }}       # ← "how many copies I want"
  template:
    spec:
      containers:
        - name: arangodb
          image: {{ .Values.image.repository }}:{{ .Values.image.tag }}
          env:
            - name: ARANGO_ROOT_PASSWORD
              valueFrom:
                secretKeyRef: { name: arangodb, key: root-password }  # ← inject a Secret
          volumeMounts:
            - { name: arango-data, mountPath: /var/lib/arangodb3 }    # ← mount storage
      volumes:
        - name: arango-data
          persistentVolumeClaim: { claimName: arangodb-pvc }          # ← durable disk
```

(The `{{ .Values.xxx }}` is Helm templating — [4.4](4.4-helm.md). Ignore it for
now; focus on the K8s shape.) You already understand `replicas` (scaling),
`image` (from [4.2](4.2-containers-and-docker.md)), `env`/Secret (config,
[4.5](4.5-configuration-and-secrets.md)), and volumes (persistence). **You know
every concept in this manifest already** — K8s just gives them declarative names.

### Service — "a stable name/address for a set of Pods"

Here's the problem a **Service** solves: Pods are ephemeral. They die and get
replaced with **new IPs**. So how does anything reliably reach "the rule-executer"
when its Pods keep changing IPs? A **Service** is a **stable name and virtual IP**
that always routes to the currently-alive Pods behind it. It's the in-cluster
**load balancer** + **DNS name** ([4.1](4.1-networking-from-zero.md)).

This is the payoff of "names outlive IPs" from
[4.1](4.1-networking-from-zero.md): other services connect to the Service *name*
(`nats`, `core-postgres`), and K8s routes to whichever Pods are currently up.
Tazama's EKS chart defines **41 Services** — one stable front for each component.

### ConfigMap & Secret — "configuration, separate from the image"

- A **ConfigMap** holds non-secret config (env values, config files) *outside*
  the image, so you change config without rebuilding ([4.5](4.5-configuration-and-secrets.md)).
  Tazama's EKS chart has **44 ConfigMaps**.
- A **Secret** holds sensitive values (passwords, tokens) — same idea, but marked
  sensitive and mountable via `secretKeyRef` (you saw `ARANGO_ROOT_PASSWORD`
  above). Tazama's chart has **36 Secrets**.

This is *the* answer to your "how do config maps work?" question: a ConfigMap is
just a named bag of key/values that K8s injects into your Pods as env vars or
files, kept separate from the code image. Change the ConfigMap → restart the
Pods → new config, no rebuild.

### StatefulSet — "for the stores that can't be treated as identical"

A Deployment's Pods are interchangeable cattle. But a **database cluster** node
isn't — node 2 has *different data* than node 1, needs a **stable identity** and
its **own persistent disk**. A **StatefulSet** gives each Pod a stable name
(`nats-0`, `nats-1`) and its own storage. Tazama runs **NATS** and stateful
stores as StatefulSets (`charts/nats/templates/statefulset.yaml`).

> **The Module 1.4 lesson made concrete:** stateless services → **Deployments**
> (cattle, freely replaced); stateful stores → **StatefulSets** (pets, stable
> identity + disk). K8s bakes the stateless/stateful distinction right into which
> object you pick.

### The rest (name-recognition is enough for now)

Tazama's chart also uses: **Ingress** (14 — the public HTTP front door /
reverse-proxy routing, [4.1](4.1-networking-from-zero.md)), **PersistentVolumeClaim**
(8 — "I need this much durable disk"), **HorizontalPodAutoscaler** (6 — "add Pods
automatically when CPU is high" = automatic horizontal scaling from
[1.2](../01-foundations/1.2-latency-throughput-numbers.md)!), **NetworkPolicy**
(20 — firewall rules for which Pods may talk to which), **PodDisruptionBudget**
(14 — "never take down so many at once that I lose availability"
[1.5](../01-foundations/1.5-design-for-failure.md)), **ServiceAccount/Role/
RoleBinding** (RBAC — who/what is allowed to do what), **Namespace** (logical
partitions like `development`, `processor`), **Job/CronJob** (run-once /
scheduled tasks).

You don't need to master these now. Just recognize that **each is a small
declarative YAML object**, and notice how many of them are *Module 1 concepts
wearing a K8s hat*: autoscaling, disruption budgets, network policies, RBAC — all
the failure/scaling/security ideas you already have.

## How it self-heals (tying it together)

```
You declare:   "3 replicas of rule-executer, image v2, behind Service 'rule-011'"
K8s observes:  only 2 Pods are running (one crashed)
K8s acts:      starts a 3rd Pod, updates the Service to route to all 3
You did:       nothing. The control loop handled it.
```

That loop, running for every object you declared, *is* Kubernetes. Everything
else is detail.
