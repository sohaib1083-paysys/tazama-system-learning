# 4.4 — Helm: templating Kubernetes

## The problem Helm solves

In [4.3](4.3-kubernetes-from-first-principles.md) you saw Tazama's chart has
**dozens of each resource** — 41 Services, 44 ConfigMaps, 36 Secrets, 13
Deployments… Writing all that YAML by hand, per environment (dev/staging/prod,
AWS/Azure/GCP), copy-pasting with tiny differences, is a nightmare. Change one
common value and you edit 50 files.

**Helm is the package manager + templating engine for Kubernetes.** It lets you:

1. **Template** the YAML — write it once with `{{ placeholders }}`, fill values
   in per environment.
2. **Package** a whole app (all its manifests) as a **chart** — one installable
   unit.
3. **Compose** charts from sub-charts (dependencies).
4. **Version, install, upgrade, and roll back** the whole app as one release.

Think: a Dockerfile builds one image; a **Helm chart** describes a whole
*application* of many K8s objects, parameterized.

---

## The three parts of a chart

```
mychart/
├── Chart.yaml       ← metadata: name, version, and DEPENDENCIES (sub-charts)
├── values.yaml      ← the DEFAULT configuration values (the knobs)
└── templates/       ← the K8s YAML, with {{ }} placeholders filled from values
```

The mechanism, in one sentence: **`templates/` + `values.yaml` → rendered
Kubernetes YAML.** Helm merges your values into the templates and hands the
result to Kubernetes.

You already saw a template in action. Recall the Tazama Deployment:

```yaml
spec:
  replicas: {{ .Values.arangodb.replicas }}          # ← pulled from values.yaml
  containers:
    - image: {{ .Values.image.repository }}:{{ .Values.image.tag }}
```

`{{ .Values.arangodb.replicas }}` means "look up `arangodb.replicas` in the
values." So to run 5 replicas in prod and 1 in dev, you don't touch the template
— you change **one line in a values file**. That's the entire point.

## Tazama's chart structure (a great real example)

Tazama has **three parallel umbrella charts**, one per cloud:

- `.../FST-performance/tazama-lf/EKS-helm/` (AWS)
- `.../FST-performance/tazama-lf/AKS-helm/` (Azure)
- `.../FST-performance/tazama-lf/GKE-helm/` (Google)

Each is an **umbrella (parent) chart**: it barely has templates of its own;
instead its `Chart.yaml` declares a long list of **dependencies** — each a
**sub-chart** for one component:

```yaml
# EKS-helm/Chart.yaml
apiVersion: v2
name: FRMS
version: 1.0.0
description: This is the subchart to install all the different software systems for FRMS.
dependencies:
  - name: arangodb   version: 1.0.0    repository: charts/arangodb-1.0.0.tgz
  - name: nats       version: 0.19.16  repository: charts/nats-0.19.16.tgz
  - name: redis      version: 9.1.3    repository: charts/redis-cluster-9.1.3.tgz
  - name: keycloak / elasticsearch / kibana / grafana / prometheus / vault / jenkins / nginx-ingress ...
```

This is **chart composition** and it's excellent design — each component
(ArangoDB, NATS, Redis, Keycloak…) is its own self-contained sub-chart under
`charts/`, and the umbrella just **assembles** them. Same cohesion/composition
instinct as the code and the compose files ([1.3](../01-foundations/1.3-coupling-and-services.md)).
The real templates live *inside each sub-chart's* `templates/` folder — which is
why there's no big top-level `templates/`.

### Turning things on and off from values

The umbrella `values.yaml` toggles each sub-chart with an `enabled:` flag and
points at its image:

```yaml
# EKS-helm/values.yaml
arangodb:
  enabled: true
  image: { repository: charts/arangodb-1.0.0.tgz, tag: 2.0.0 }
```

So the same chart can deploy "everything" or "just the core" by flipping
`enabled` flags — **one chart, many deployment shapes, driven by values.** That's
the whole philosophy: *structure in templates, choices in values.*

## The Helm workflow (commands you'll actually run)

```bash
helm install frms ./EKS-helm            # render templates + values, apply to cluster
helm upgrade frms ./EKS-helm            # apply changes as a new "revision"
helm rollback frms 1                    # go back to revision 1 (instant undo!)
helm install frms ./EKS-helm \
     --set arangodb.replicas=5          # override a value at install time
helm template ./EKS-helm                # just RENDER the YAML locally (don't apply) — great for learning
```

Two things to notice as a senior habit:

- **`helm rollback`** — because Helm versions each release, a bad deploy is *one
  command* to undo. This is [1.5](../01-foundations/1.5-design-for-failure.md)
  design-for-failure at the deployment level: *always have a fast way back.*
- **`helm template`** — renders the final YAML *without touching a cluster*. This
  is the single best way to learn: run it on Tazama's chart and read the fully-
  rendered Kubernetes manifests, no cluster needed.

## Helm era vs Compose era (the honest picture)

Remember from Module 3: Tazama has **two deployment eras**.

| | **Helm charts** (`FST-performance/…`) | **Docker Compose** (`tazama-stack/…`) |
|---|---|---|
| Runs on | Kubernetes (many machines) | One machine (dev/local) |
| Database | **ArangoDB** | **PostgreSQL** |
| Cache | Redis | Valkey |
| Best for learning | K8s resources, Helm templating, RBAC | the current app services & wiring |

Both are valid teaching artifacts. The **compose stack** shows you the *current*
services and how they wire; the **Helm charts** show you *Kubernetes and Helm* in
a rich, real example. Use each for what it teaches — and notice the drift, which
is itself the senior skill of "docs/infra reflect different points in time."
