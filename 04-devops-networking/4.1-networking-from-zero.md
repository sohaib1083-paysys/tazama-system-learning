# 4.1 — Networking from zero

You said you don't know how networking works. Perfect — we start from truly
zero and build up only what you need to understand systems like Tazama. No
memorizing; just the mental models.

## The one question networking answers

> **"I have data here. How does it get to a specific program running on a
> specific machine somewhere else?"**

Everything below is the layered answer to that.

---

## Layer 1: machines have addresses — IP addresses

Every machine on a network has an **IP address** — like a postal address.
- `192.168.1.42` (IPv4) or a longer IPv6 form.
- `127.0.0.1` is special: it means **"this same machine"** (aka `localhost`).

When two Tazama services on different machines talk, packets are addressed to the
other machine's IP. But an IP gets you to the *machine* — not to the right
*program* on it. That's the next layer.

---

## Layer 2: programs listen on ports

A **port** is a number (0–65535) that identifies a *specific program* on a
machine. Think: the IP is the building address, the port is the apartment number.

- The Event Monitoring Service listens on port **3002**.
- PostgreSQL listens on **5432**. Redis/Valkey on **6379**. NATS on **4222**.

So `10.10.80.37:4222` means "the NATS program on machine 10.10.80.37." You saw
exactly this in Tazama's config: `SERVER_URL=nats://10.10.80.37:14222`. Now you
can *read* that: protocol `nats`, machine `10.10.80.37`, port `14222`.

A program **"binds"** to a port to listen; a client **"connects"** to that
`ip:port`. Two programs can't listen on the same port on the same machine —
that's the "address already in use" error you'll eventually hit.

---

## Layer 3: names, not numbers — DNS

Humans and configs don't want to hardcode IPs (they change). **DNS** (Domain
Name System) is the internet's phone book: it translates a **name** →
an **IP address**.

- `nats://nats:4222` — the name `nats` gets resolved to an IP.
- Where does `nats` resolve? **This is the key insight for containers:** inside a
  Docker/Kubernetes network, **service names are DNS names.** When a Tazama
  service connects to host `valkey` or `core-postgres` or `event-sidecar`, those
  aren't IPs — they're *service names* that the container network's DNS resolves
  to whatever IP that container currently has.

That's why Tazama's config says `REDIS_SERVERS=[{"host":"valkey","port":6379}]` —
"valkey" is a **name**, resolved by the container network. The container could be
rescheduled to a new IP and the name still works. **This is the whole reason
service discovery works in containers: names outlive IPs.** Hold onto this — it's
the single most useful networking fact for understanding Kubernetes.

---

## Layer 4: the conversation — TCP (and UDP)

Once you can reach `ip:port`, how does data actually flow reliably?

- **TCP** — a **reliable, ordered** connection. It guarantees your bytes arrive,
  in order, or you're told it failed. It does this with acknowledgments and
  retransmission (sound familiar? same idea as JetStream acks). HTTP, PostgreSQL,
  NATS all run over TCP.
- **UDP** — **fire-and-forget**, no guarantee. Faster, used for things like video
  or DNS where a lost packet doesn't matter much.

You rarely touch TCP directly, but knowing "TCP = reliable ordered stream" and
"UDP = fast lossy datagrams" is enough to reason about most systems. (Notice the
parallel: TCP:UDP :: JetStream:CoreNATS. The same reliability-vs-speed tradeoff
appears at every layer.)

---

## Layer 5: the language on top — HTTP

**HTTP** is the request/response protocol of the web, running over TCP. A request
is just text with a shape:

```
POST /dems-engine/tenant01,pacs,008,001,10 HTTP/1.1   ← method + path
Host: tms.example.com                                  ← headers
Authorization: Bearer eyJ...                           ← (the JWT!)
Content-Type: application/json

{ "transaction": ... }                                 ← body
```

The response comes back with a **status code**:
- `2xx` success (`200 OK`, `201 Created`, `202 Accepted`)
- `4xx` **you** messed up (`400` bad request, `401` unauthorized, `404` not found)
- `5xx` **the server** messed up (`500` internal error, `503` unavailable)

You already met this exact request in [2.2](../02-tazama-architecture/2.2-transaction-journey.md)
— the transaction arriving at Tazama's front door. Now you can read every part of
it. The `Authorization: Bearer` header carries the **JWT** that Keycloak issued
and `TazamaAuthGuard` checks.

---

## Putting it together: what happens when a bank calls Tazama

1. The bank's system has Tazama's front-door **name** → DNS resolves it to an
   **IP**.
2. It opens a **TCP** connection to that **IP** on the API's **port**.
3. It sends an **HTTP POST** with the transaction in the body and a JWT in a
   header.
4. The Event Monitoring Service, **listening** on that port, accepts it, checks
   the JWT, and responds with a status code.
5. From there it's NATS (also TCP, to `nats:4222`) the rest of the way.

That's the full networking story of Tazama's edge — and you built it from IP →
port → DNS → TCP → HTTP.

---

## Two more concepts you'll meet immediately

### Load balancer

When you run 20 copies of a service, something must spread incoming connections
across them. A **load balancer** sits in front, takes each connection, and picks
a backend copy (round-robin, least-connections, etc.). It also stops sending to
copies that fail health checks ([1.5](../01-foundations/1.5-design-for-failure.md)).
Tazama's infra spec lists load balancers; in Kubernetes this role is played by a
**Service** + **Ingress** ([4.3](4.3-kubernetes-from-first-principles.md)).

### Reverse proxy / ingress

A **reverse proxy** (like **nginx**) is the single public front door that routes
incoming requests to the right internal service by hostname/path, terminates
HTTPS, and shields your internals. Tazama's older stack uses an **nginx ingress
controller** for exactly this. Think of it as the receptionist: everyone comes to
one desk, and it directs them inside.
