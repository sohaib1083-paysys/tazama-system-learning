# 4.5 — Configuration: env vars, config maps & secrets — done right

## The principle: config is separate from code

A famous set of guidelines called the **Twelve-Factor App** states it best:

> **Store configuration in the environment, not in the code.**

Why? Because the *same image* must run in dev, staging, and prod — pointing at
different databases, different NATS servers, different tenants — **without
rebuilding**. If the database hostname were hardcoded in the code, you'd need a
different build per environment. Instead, the code reads `RAW_HISTORY_DATABASE_HOST`
from the environment, and *the environment* differs per deployment.

This is why in [4.2](4.2-containers-and-docker.md) the rule-executer image bakes
in **defaults** but everything real comes from **env vars** at run time. Build
once, configure per place.

## The four layers of config in Tazama (a great comparison)

Tazama injects config four ways. Seeing all four side by side teaches the whole
topic:

### 1. Per-service `.env` files (the main mechanism in the compose stack)

Each service loads its own env file plus a shared one:

```yaml
# in docker-compose.dev.core.yaml
env_file:
  - env/tms-service.env
  - .env
```

And `env/tms-service.env` looks like:

```
FUNCTION_NAME=transaction-monitoring-service
SIDECAR_HOST=event-sidecar:${EVENT_SIDECAR_PORT}
REDIS_SERVERS=[{"host":"valkey", "port":6379}]
RAW_HISTORY_DATABASE_HOST=core-postgres
RAW_HISTORY_DATABASE_USER=postgres
```

Read it with your Module 3/4 eyes: it tells the service **where its cache is**
(`valkey`), **where its database is** (`core-postgres`) — by **name**
([4.1](4.1-networking-from-zero.md)), and **who it is** (`FUNCTION_NAME`). This
one file *is* the service's wiring into the system.

### 2. A global `.env` for shared values & interpolation

`/home/sohaib/Documents/frms/tazama-stack/core/.env` drives ports, versions, and
branch selection, and gets **interpolated** into the others (note the
`${EVENT_SIDECAR_PORT}` above):

```
TAZAMA_VERSION=rc
TMS_BRANCH=dev
TMS_PORT=5000
EVENT_SIDECAR_PORT=15000
```

One place to bump a version or flip a branch, referenced everywhere. That's DRY
(don't repeat yourself) applied to config.

### 3. Defaults baked into the Dockerfile

The image ships sane defaults so it runs even with minimal config:

```dockerfile
ENV FUNCTION_NAME="rule-executer"
ENV NODE_ENV=production
```

**Precedence** (senior detail): runtime env (`.env` file / ConfigMap) **overrides**
the Dockerfile `ENV` defaults. So the image is self-sufficient but every value is
externally overridable. Layered defaults with clear precedence = robust config.

### 4. Kubernetes-native: ConfigMaps & Secrets (the Helm era)

On Kubernetes, the same job is done by **ConfigMaps** (non-secret) and **Secrets**
(sensitive), injected into Pods. You saw the Secret injection in
[4.3](4.3-kubernetes-from-first-principles.md):

```yaml
env:
  - name: ARANGO_ROOT_PASSWORD
    valueFrom:
      secretKeyRef: { name: arangodb, key: root-password }   # pulled from a Secret
```

**So "config map" now has a clear answer for you:** it's Kubernetes' way of
holding non-secret config outside the image and injecting it into containers as
env vars or mounted files — the K8s equivalent of a `.env` file. A **Secret** is
the same but for sensitive values.

## The config vs secret distinction — and why it's a security boundary

- **Config** (non-sensitive): hostnames, ports, feature flags, tenant IDs,
  timeouts, TTLs. Fine to commit to git (in `.env.template` form), fine to log.
- **Secret** (sensitive): database passwords, JWT signing keys, API tokens,
  `GH_TOKEN`. **Must never** be committed to git, never logged, never baked into
  an image.

Notice Tazama's discipline here:
- The `tazama-personal/*` repos ship **`.env.template`** files — the checked-in,
  **secret-free** starting point. You copy it to `.env` and fill in real secrets
  locally, and `.env` is gitignored. **The template is committed; the filled-in
  secrets are not.** That's the correct pattern — steal it.
- The compose build uses a **build secret** (`secrets: [GH_TOKEN]`) rather than
  putting the token in a plain env var or the image, so it doesn't get baked into
  a layer.
- K8s **Secrets** are a separate object type from ConfigMaps precisely so access
  can be restricted differently (RBAC).

> **The rule to internalize:** a secret in your git history is a secret that's
> leaked — permanently, because git remembers. The whole `.env.template` +
> gitignored-`.env` + K8s-Secret machinery exists to keep secrets **out of code
> and out of history**. This is one of the most common real-world security
> failures, and now you know the standard defense.

---

## For production secrets: a vault

`.env` files and K8s Secrets are fine, but K8s Secrets are only base64-encoded by
default (not encrypted at rest without extra config). For serious production,
teams add a **secrets manager** like **HashiCorp Vault** (which Tazama's Helm
dependencies include) or a cloud KMS. Vault stores secrets encrypted, controls
access tightly, and can **rotate** them. You don't need it to start, but know the
progression: **hardcoded (never) → env file → K8s Secret → Vault/KMS**, each more
secure and more operationally involved.
