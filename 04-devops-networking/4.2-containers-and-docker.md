# 4.2 — Containers & Docker: what an image *really* is

## The problem containers solve

You've heard "it works on my machine." Containers are the fix. The problem:
software depends on a specific OS, specific libraries, specific versions, specific
env vars. Move it to another machine and something's different → it breaks.

A **container** packages your program **together with everything it needs to
run** — the right Node version, the right libraries, the right files — into one
sealed unit that runs **identically anywhere** Docker runs. Your laptop, a
teammate's, the CI server, production: same container, same behavior.

---

## Image vs container (the distinction that trips everyone up)

- An **image** is the *blueprint* — a frozen, read-only snapshot of a filesystem
  plus "how to start it." It's a file you build once and store.
- A **container** is a *running instance* of an image — like an object is an
  instance of a class.

One image → many containers. Tazama builds a rule-executer **image** once, then
runs **N containers** from it to scale ([1.4](../01-foundations/1.4-state-the-hard-problem.md)
statelessness makes this safe). Build once, run many.

---

## What an image actually is: layers

An image is built in **layers**, each layer a set of filesystem changes stacked
on the previous. This matters for two practical reasons:

1. **Caching** — if a layer hasn't changed, Docker reuses it instead of rebuilding.
   Order your build so the rarely-changing stuff (installing dependencies) is in
   *early* layers and the frequently-changing stuff (your source code) is *late* —
   then a code change only rebuilds the last cheap layers. You'll see Tazama do
   this.
2. **Sharing** — many images share common base layers, so you don't store 10
   copies of the Node runtime.

## Reading a real Tazama Dockerfile

A **Dockerfile** is the recipe for an image. Here's the actual rule-executer one
(`/home/sohaib/Documents/frms/tazama-personal/rule-executer/Dockerfile`),
annotated. This is a **multi-stage build**, which is the professional pattern —
read it top to bottom:

```dockerfile
ARG BUILD_IMAGE=node:20-bullseye                          # full Node image to BUILD with
ARG RUN_IMAGE=gcr.io/distroless/nodejs20-debian11:nonroot # tiny image to RUN in

# ── Stage 1: build (compile TypeScript → JavaScript) ──
FROM ${BUILD_IMAGE} AS builder
WORKDIR /home/app
COPY ./src ./src
COPY ./package*.json ./tsconfig.json ./
RUN npm ci --ignore-scripts && npm run build          # install ALL deps, compile

# ── Stage 2: resolve production-only dependencies ──
FROM ${BUILD_IMAGE} AS dep-resolver
RUN npm ci --omit=dev --ignore-scripts                # only the deps needed at RUNTIME

# ── Stage 3: the final, minimal runtime image ──
FROM ${RUN_IMAGE} AS run-env
USER nonroot                                          # don't run as root!
COPY --from=dep-resolver /node_modules ./node_modules # copy only prod deps
COPY --from=builder      /home/app/build ./build      # copy only compiled output
ENV FUNCTION_NAME="rule-executer"
ENV NODE_ENV=production
CMD ["build/index.js"]                                # how to start the container
```

Every line here is a deliberate, senior-grade decision:

- **Multi-stage** (`AS builder`, `AS dep-resolver`, `AS run-env`): you build with
  a big toolchain image but **ship** only the tiny final stage. The compiler,
  dev dependencies, and source `.ts` files **never make it into the shipped
  image**. Result: smaller, faster to pull, less to attack.
- **Distroless base** (`gcr.io/distroless`): the final image has **no shell, no
  package manager, almost nothing** but the Node runtime and your app. You can't
  `bash` into it — because an attacker can't either. Minimal **attack surface**.
- **`USER nonroot`**: the container doesn't run as root. If someone breaks in,
  they're not root. **Least privilege** ([3.3](../03-messaging-and-data/3.3-databases.md))
  at the OS level.
- **`npm ci --omit=dev`**: ship only runtime dependencies, not the dev toolchain.
- **`ENV ... NODE_ENV=production`**: sane defaults baked in ([4.5](4.5-configuration-and-secrets.md)).
- **`CMD`**: the one process the container runs. A container ideally runs **one
  process** — that's the "one container, one job" convention (cohesion again,
  [1.3](../01-foundations/1.3-coupling-and-services.md)).

Every Tazama Node service (`tms-service`, `event-director`, `typology-processor`,
`admin-service`…) uses this **same three-stage template**. Consistency again —
learn one Dockerfile, you can read them all.

## Where images live: registries

You build an image, then **push** it to a **container registry** (Docker Hub, a
cloud registry, a private one). Other machines **pull** it. It's `git push`/`git
pull` but for images. Tazama's infra spec lists a **Container Registry**; the
compose files reference both Docker Hub images (`docker-compose.hub.*.yaml`) and
build-from-source variants (`docker-compose.dev.*.yaml`).

Interesting Tazama detail: the dev compose files **build images straight from
GitHub URLs** at deploy time, using a `GH_TOKEN` build secret:

```yaml
build:
  context: https://github.com/tazama-lf/tms-service.git#${TMS_BRANCH}
  secrets: [GH_TOKEN]
```

That's a neat pattern: pin each service to a **git branch** via an env var and
build on the spot — great for testing feature branches without publishing images.

## Docker Compose: running many containers together

One container is a service. A *system* is many containers that must run together
and talk. **Docker Compose** describes a whole multi-container setup in YAML — and
this is Tazama's **primary local/dev deployment**:

```yaml
# docker-compose.base.infrastructure.yaml (the backing stores)
services:
  valkey:          # the cache
    image: valkey/valkey:7.2.5
    healthcheck: { test: ["CMD-SHELL", "valkey-cli -p 6379 ping | grep PONG"], ... }
  core-postgres:   # the database
    image: postgres:18
    volumes: [ "./postgres/migration/base:/docker-entrypoint-initdb.d" ]
  nats:            # the message bus
    image: nats:2
```

Read that and you see the **whole infrastructure of Tazama** in a dozen lines:
cache + database + message bus, exactly the trio from Module 3. Key Compose
concepts visible here:

- **`image:`** — which image to run (an off-the-shelf one here; Tazama doesn't
  rebuild Postgres — design principle #2, don't reinvent).
- **`healthcheck:`** — how Docker knows a container is *actually ready*, not just
  started. `depends_on: { condition: service_healthy }` makes services wait for
  Postgres to be truly up before starting ([1.5](../01-foundations/1.5-design-for-failure.md)
  — ordering under failure).
- **`volumes:`** — mount files/data into the container. Here it seeds Postgres
  with migration SQL. Volumes are also how a container keeps **data that survives
  restarts** (the container is ephemeral; the volume persists — this is how you
  make a *stateful* store out of ephemeral containers).
- **networking** — all services on the compose network reach each other **by
  service name** (`valkey`, `core-postgres`, `nats`) — exactly the DNS-by-name
  point from [4.1](4.1-networking-from-zero.md).

Tazama splits this across **many small compose files** combined with `include:`
and **profiles** (infra, core app, auth, elastic, relay variants). That's
modularization applied to infra config — the same cohesion instinct as the code.
