# 3.4 — Caching & why Redis is everywhere

## The one idea behind all caching

Go back to the latency table in [1.2](../01-foundations/1.2-latency-throughput-numbers.md):

- RAM read: ~100 **nanoseconds**
- A database query over the network: ~**milliseconds** (10,000× slower or more)

**A cache is a small, fast copy of data kept close, so you avoid the slow trip
to the real source.** That's it. Every cache — CPU caches, Redis, your browser's
cache, a CDN — is the same idea at a different scale: *trade a little memory and
some staleness for a lot of speed.*

---

## Where Tazama caches, and why it must

Look at the Event Director's hottest operation ([2.2](../02-tazama-architecture/2.2-transaction-journey.md)):
**every single transaction** needs the **network map** (which rules apply). If it
fetched that from PostgreSQL on every transaction, at 3,000 tx/s that's 3,000
identical DB queries per second for data that barely changes. Insane waste.

So Tazama caches the network map in **two layers**:

1. **`node-cache`** — an *in-process* cache (inside the service's own memory).
   Fastest possible: no network hop at all, just a RAM read.
2. **Redis / Valkey** — a *shared* cache (a separate fast in-memory store all
   copies of the service can reach). Survives across service instances.

The lookup order is a classic **cache hierarchy**:

```
network map needed?
  ├─ in local node-cache?  → use it            (nanoseconds, no network)
  ├─ else in Redis/Valkey? → use it, fill local (microseconds, one hop)
  └─ else                  → query PostgreSQL, fill both  (milliseconds)
```

Each layer is faster and closer than the one below. Most requests never touch
Postgres. **This is why Tazama can hit its throughput targets** — the expensive
store is protected by cheap fast copies in front of it.

The cache key is `${tenantId}:${txTp}` — note it's **multi-tenant aware** so
tenant A's cached config never bleeds into tenant B. Cache-key design is a real
skill: the key must capture *everything that makes the value different*, or
you'll serve the wrong data.

---

## Redis vs Valkey (the naming thing you'll hit)

You'll see both. **Valkey** is an open-source **fork of Redis**, created when
Redis changed its license — remember Tazama's design principle #1, "Open Source
First," and #2, "don't depend on tools that might change licensing terms"? This
is that principle *in action*: Tazama's newer stack runs **Valkey** (still
Redis-compatible) to stay on a permissive license. But the code's client library
is literally `ioredis` and the env vars are still `REDIS_*` — because Valkey
speaks the Redis protocol. So: *Valkey the server, Redis the protocol, ioredis
the client.* Same thing, three names — now it won't confuse you.

---

## The hard part of caching: invalidation

> "There are only two hard things in computer science: cache invalidation and
> naming things." — Phil Karlton (only half joking)

A cache holds a *copy*. When the real data changes, the copy is **stale**. How do
you handle that? The main strategies:

- **TTL (time-to-live)** — the copy auto-expires after N seconds. Simple, and
  good when "slightly stale is fine." Tazama's caches use TTLs (you'll see cache
  TTL env vars baked into the Dockerfiles). If the network map changes, worst
  case you serve the old one for up to the TTL.
- **Explicit invalidation** — when data changes, actively delete/update the cache
  entry. More correct, more complex (you must find every cache that has a copy).
- **Write-through** — write to the cache and the DB together, so they never
  diverge.

The tradeoff is **consistency vs simplicity** ([1.4](../01-foundations/1.4-state-the-hard-problem.md)
CAP again): a longer TTL = fewer DB hits (faster/cheaper) but more staleness. A
shorter TTL = fresher but more load. **Choosing the TTL is choosing a point on
that curve** — and the right point depends on how bad stale data is. For a
network map that changes rarely, a generous TTL is fine. For a fraud
*decision*, you'd never cache stale.

---

## What else Redis/Valkey is used for

Redis isn't only a read-cache. In Tazama and generally it's used for:

- **Caching** (the main use above).
- **Session storage** (the CMS uses it for sessions) — fast, shared, expirable.
- **Deduplication / short-term state** — "have I seen this ID recently?"
- Redis can also do pub/sub, rate limiting, locks, counters — it's a Swiss army
  knife *because* in-memory data structures are so fast.

The through-line: **anything that needs to be fast and shared and can tolerate
living in memory** is a candidate for Redis/Valkey.

---

## When NOT to cache

Senior balance — caching adds a moving part and a staleness risk, so don't cache
reflexively:

- Data that **must** be perfectly fresh (a live account balance you're about to
  debit).
- Data that changes **every read** (no reuse = no benefit).
- Data cheap to compute anyway.

A cache you don't need is complexity and a bug surface (stale reads) for no gain.
Cache the **hot, reused, tolerant-of-slight-staleness** data — like a network
map read 3,000 times a second.
