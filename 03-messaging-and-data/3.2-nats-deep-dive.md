# 3.2 — NATS deep dive, as Tazama uses it

NATS is Tazama's nervous system. This lesson makes it concrete: what NATS is,
its core concepts, and exactly how Tazama's `frms-coe-startup-lib` wraps it.

## What NATS is (and why Tazama picked it)

NATS is a lightweight, high-performance **messaging system**. A central **NATS
server** (or cluster) relays messages between **clients**. Clients don't know
each other's network locations — they only know **subjects** (string addresses).

Tazama picked it deliberately, and the reasons are in the design principles you
read in Module 1: it's **open source with a permissive license**, **battle-tested**,
**fast**, and **doesn't need forking**. Re-read design principle #2 ("Do not
reinvent a serviceable wheel") — NATS is the named example.

## The core NATS concepts

### Subjects — the addressing scheme

A **subject** is a dot-separated string like `event-director` or
`sub-rule-011@1.0.0`. Publishers publish *to* a subject; subscribers subscribe
*to* a subject. That's the whole addressing model — no IP addresses, no
hostnames in your app code.

Subjects support **wildcards**:
- `*` matches one token: `rule.*.result` matches `rule.011.result`.
- `>` matches the rest: `rule.>` matches `rule.011.result.detail`.

Tazama uses **computed subjects**: `sub-rule-${RULE_NAME}@${RULE_VERSION}`. The
version is *in the subject*, so rule-011 v1 and v2 are different subjects and can
run side by side ([1.3](../01-foundations/1.3-coupling-and-services.md) —
versioned contracts). This is a small idea with big consequences: **you deploy a
new rule version by pointing a new deployment at a new subject**, no coordination
flag-day.

### Core NATS vs JetStream — the crucial distinction

| | **Core NATS** | **JetStream** |
|---|---|---|
| Delivery | Fire-and-forget | **Persisted** to disk |
| If no subscriber is listening | Message is **lost** | Message is **stored**, delivered later |
| If a consumer crashes mid-process | Message is **gone** | **Redelivered** (until acked) |
| Replay | No | Yes |
| Speed | Fastest | Slightly slower (durability costs) |

Plain Core NATS is "at-most-once" — blazing fast but a message with no listener
just vanishes. **JetStream** adds a durable **stream** (a log of messages) and
**consumers** that track their position and **ack** each message. This is what
lets Tazama say "a rule can be down and the transaction waits instead of being
lost" — the failure-absorption you learned in
[1.5](../01-foundations/1.5-design-for-failure.md).

Tazama's factory lets a service pick either via the `SERVER_TYPE` env var
(`'nats'` or `'jetstream'`) — so the *same code* can run fire-and-forget in a
throwaway dev setup or durable in production.

### Queue groups — load-sharing across copies

If 30 copies of rule-011 all subscribe to `sub-rule-011@1.0.0` as a **queue
group**, NATS delivers each message to **exactly one** of them (Pattern B from
[3.1](3.1-messaging-models.md)). That's how horizontal scaling of a stateless
processor actually load-balances. Without a queue group, all 30 would each get
*every* message (pub-sub, Pattern A) — which you'd want for *different*
consumers, not copies of the same one. **Same subject, different grouping,
opposite behavior** — worth internalizing.

### Ack — the durability handshake

With JetStream, after your handler finishes, it **acks** the message. Until then
JetStream considers it un-processed. Crash before ack → redelivery. You saw the
exact line in [2.3](../02-tazama-architecture/2.3-processor-pattern.md):

```ts
for await (const message of sub) {
  const request = message.json<string>();
  onMessage(request, (msg) => { void this.handleResponse(msg); });
  message.ack();   // ← "I've safely handled it; JetStream can forget it"
}
```

This one call is the difference between "we lose transactions when a pod
restarts" and "we don't."

## How Tazama wraps NATS (the two calls, again, but deeper)

Everything a Tazama service does with NATS goes through **three methods**
([2.3](../02-tazama-architecture/2.3-processor-pattern.md)):

```ts
// frms-coe-startup-lib/src/interfaces/iStartupService.ts
init:           (onMessage, logger?, consumerSubjects?, producerSubject?) => Promise<boolean>;
initProducer:   (logger?, producerSubject?) => Promise<boolean>;
handleResponse: (response, subject?) => Promise<void>;
```

- **`init`** = "subscribe me to these subjects; call `onMessage` for each; and
  set up my producer stream." → **consuming**.
- **`handleResponse(payload, [subjects])`** = "publish this to my producer
  stream, and also to these extra subjects." → **producing / routing**.

And the payload is **protobuf-encoded** before publishing:

```ts
// jetstreamService.ts
async handleResponse(response, subject?) {
  const res = ...encode(response);                          // protobuf: compact + fast
  publishes.push(this.js.publish(this.producerStreamName, sc.encode(res)));
  if (subject) for (const sub of subject) publishes.push(this.js.publish(sub, sc.encode(res)));
  await Promise.all(publishes);
}
```

Why **protobuf** and not JSON? Messages fly across the bus thousands of times per
second. Protobuf is a **binary** format — smaller on the wire and faster to
encode/decode than text JSON. At 3,000 tx/s × many hops, that efficiency is real
money and real latency ([1.2](../01-foundations/1.2-latency-throughput-numbers.md)).
This is "avoid obvious bottlenecks" (design principle #3) in a single choice.

## The relay services (a bonus pattern worth knowing)

Tazama also has **relay services** — adapters that take messages off NATS and
push them to *other* systems (REST, Kafka, RabbitMQ, BigQuery). This is the
**adapter / bridge** pattern: your internal bus stays NATS, but you can *emit* to
whatever an integration partner speaks, without your core services knowing. It's
the same "abstract the outside world at the edge" idea as the front-door
normalizer ([2.2](../02-tazama-architecture/2.2-transaction-journey.md)), applied
on the way *out*.

## Mental model to keep

```
        subject = the address (a string, versioned)
        Core NATS = fast, lossy         JetStream = durable, ack'd, replayable
        pub-sub   = every subscriber    queue group = one of N copies
        ack       = "safely handled"    protobuf    = compact binary payloads
```

If you hold those six pairs, you understand Tazama's messaging better than most
people who work on it.
