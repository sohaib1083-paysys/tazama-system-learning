# 3.3 — Databases: pick the right shape

State has to live somewhere. This lesson is the mental model for **choosing a
database**, then grounded in the several databases Tazama actually runs.

## First principle: databases are shaped for different questions

There is no "best database." There are databases **shaped** for different access
patterns. Pick by asking: *what questions will I ask of this data, and how fast,
how often, and how consistently?*

The main families:

| Family | Shaped for | Example | Tazama uses |
|---|---|---|---|
| **Relational (SQL)** | Structured rows, relationships, transactions, ad-hoc queries | PostgreSQL | ✅ Primary store (current) |
| **Document** | Nested JSON blobs, flexible schema | CouchDB, Mongo | ✅ CouchDB for case evidence |
| **Key-value / cache** | "Give me the value for this key" — blazing fast | Redis / Valkey | ✅ Hot lookups, caching |
| **Multi-model / graph** | Documents *and* relationships as a graph | ArangoDB | ✅ Older Tazama store |
| **Search** | Full-text / analytical search over lots of docs | OpenSearch, Elastic | ✅ CMS audit logs |
| **Column / analytics** | Aggregations over huge datasets | BigQuery | ✅ Via a relay (analytics) |

Notice Tazama uses **six different database technologies**. That's not chaos —
it's **polyglot persistence**: use the store shaped for each job. The senior
skill is resisting "one database for everything" *and* resisting "a new database
for every whim." Each store you add is operational weight ([1.3](../01-foundations/1.3-coupling-and-services.md)).

## Relational (PostgreSQL): the workhorse

Tazama's **current** primary store is **PostgreSQL**, holding three logical
databases:

- **`raw_history`** — the raw transactions as received.
- **`event_history`** — processed events (what rules query for a participant's
  past behavior).
- **`configuration`** — the network map, rule configs, tenant settings.

Why relational for these? Because you ask **structured, relational questions**:
"all successful transactions from this creditor in the last 30 days" (rule-011
does exactly this). SQL with indexes is superb at that.

Look at how rule-011 queries it — this is a **named prepared statement**:

```ts
// rule-011 queries event_history via the shared DB manager
databaseManager._eventHistory.query<T>({ name, text, values });
```

Two senior-grade details in that one line:

1. **Prepared statements** (`text` + separate `values`) — the values are never
   string-concatenated into the SQL. This makes it **immune to SQL injection**
   *and* lets Postgres cache the query plan (faster). Never build SQL by string
   concatenation; always parameterize. This is both a **security** and a
   **performance** habit.
2. **Named** statements — Postgres caches the plan under that name, so repeated
   executions skip re-planning. At high throughput this matters.

### Indexes — the single most important DB performance concept

An **index** is a sorted lookup structure so the DB can *find* rows without
scanning every one. Without an index, "transactions for creditor X" scans the
whole table (O(n)); with an index on creditor, it jumps straight there
(~O(log n)). At millions of rows this is the difference between 5ms and 5s.

Tazama documents its indexes deliberately:
[`../../Technical/Database/postgres-db-deployment-indexes.md`](https://github.com/tazama-lf/docs/blob/main/Technical/Database/postgres-db-deployment-indexes.md).
**The habit to steal:** for every query pattern your app runs frequently, there
should be an index that supports it — and you should be able to point at it.
Read that file and notice they've matched indexes to the rules' query patterns.

## Document (CouchDB) & Search (OpenSearch): shaped for their jobs

In the Case Management System:

- **CouchDB** stores **case evidence documents** — arbitrary nested JSON that
  varies case to case. A rigid relational schema would fight you here; a document
  store flexes.
- **OpenSearch** stores **audit logs** — you need fast full-text and analytical
  search across huge volumes ("show every action on cases touching account X").
  That's a search engine's job, not a relational DB's.

Same system, three different stores, each matched to its access pattern. When you
see this, don't think "messy" — think "someone chose the right tool three times."

## The ArangoDB → PostgreSQL migration (a real-world lesson)

Older Tazama used **ArangoDB** (a multi-model DB that does documents *and* graph
in one). The current stack uses **PostgreSQL**. Both appear in the repos: the
Helm charts deploy Arango; the docker-compose stack deploys Postgres; the
`tms-configuration` bundle still references Arango constraints.

This migration is itself a lesson. Teams change databases when:
- The original choice's tradeoffs stopped fitting (cost, clustering behavior,
  operational familiarity, performance at scale).
- Tazama literally **benchmarked** the options — see
  [`../../Technical/Performance-Benchmarking/`](https://github.com/tazama-lf/docs/blob/main/Technical/Performance-Benchmarking/),
  including "ArangoDB single-instance vs split-databases vs clustering."

**The senior takeaway:** database choice is a *reversible-with-effort* decision,
and the way you make it defensible is by **measuring** (benchmarks), not by
opinion. Also: because Tazama **abstracted DB access behind `frms-coe-lib`'s DB
manager** ([1.3](../01-foundations/1.3-coupling-and-services.md), design
principle #2), swapping the underlying store didn't require rewriting every
service — they changed the abstraction's implementation. *That's the payoff of
abstracting third-party dependencies.* Feel how Module 1 keeps cashing out here.

## Least-privilege data access (a design gem)

Recall from [2.3](../02-tazama-architecture/2.3-processor-pattern.md) that a
service gets **only the stores it declares**, enforced by TypeScript:

```ts
// frms-coe-lib/src/services/dbManager.ts
type DatabaseManagerInstance<T> = ManagerStatus &
  (T extends { eventHistory: DBConfig } ? EventHistoryDB : Record<string, unknown>) &
  (T extends { configuration: DBConfig } ? ConfigurationDB : Record<string, unknown>) & ...;
```

The Event Director declares `configuration` (it reads network maps); a rule
executer declares `eventHistory` + `configuration` (history + rule config). A
service *can't* touch a store it didn't ask for. **Least privilege applied to
data** — smaller blast radius if a service is compromised or buggy. This is a
security principle (Module 6) enforced by a type system. Beautiful.
