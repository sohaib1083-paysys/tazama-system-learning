# 3.1: Messaging models: request/response vs pub-sub vs queues

You now know Tazama is glued together by messages. This lesson is the mental
toolkit for *all* inter-service communication, so you can reason about **when to
use which** — not just in Tazama, but everywhere.

## The two fundamental styles

### 1. Synchronous request/response (HTTP, gRPC)

You call, you **wait**, you get an answer. Like a phone call.

```
Client ──request──▶ Server
Client ◀─response── Server   (client blocked the whole time)
```

- **Good for:** "I need the answer *now* to continue" — a user asking for data,
  the front-door API accepting a transaction.
- **Bad for:** anything where the caller shouldn't have to wait, or where the
  receiver might be down. The caller is **coupled in time** to the receiver:
  both must be up *at the same instant*. (Recall [1.3](../01-foundations/1.3-coupling-and-services.md).)

Tazama uses this at exactly **two edges**: the HTTP `POST` into the front door
(client needs an immediate "accepted" acknowledgment), and the REST API of the
Case Management UI (an investigator clicks, needs data back). Everywhere *else*,
it deliberately doesn't.

### 2. Asynchronous messaging (NATS, Kafka, RabbitMQ)

You **drop a message** and move on. Like sending a letter or texting. Someone
picks it up when they're ready.

```
Producer ──message──▶ [ message bus ] ──▶ Consumer
   (free to continue immediately)          (processes when ready)
```

- **Good for:** pipelines, work that can happen slightly later, decoupling
  services in time, absorbing bursts, fan-out.
- The producer and consumer are **decoupled in time** — the consumer can be
  down, slow, or scaled to 20 copies, and the producer doesn't know or care.

This is Tazama's spine. Every arrow between processors in
[2.2](../02-tazama-architecture/2.2-transaction-journey.md) is async messaging.

> **The core tradeoff:** synchronous is *simpler to reason about* (you get an
> answer inline) but *couples in time and doesn't absorb failure*. Asynchronous
> is *more resilient and scalable* but *harder to reason about* (the answer
> comes later, or via another message). Senior engineers reach for sync at the
> edges and async in the guts — which is precisely Tazama's shape.

## Within async, three delivery patterns

Async messaging isn't one thing. There are three distinct patterns, and the
difference is **who receives a message**.

### Pattern A — Publish/Subscribe (pub-sub): *everyone* interested gets it

A message is published to a **subject/topic**. **Every** subscriber to that
subject gets its **own copy**.

```
                       ┌─▶ Subscriber 1 (gets a copy)
Publisher ─[subject]──▶├─▶ Subscriber 2 (gets a copy)
                       └─▶ Subscriber 3 (gets a copy)
```

- **Use when:** multiple *different* consumers each need to react to the same
  event. E.g., "transaction accepted" → the fraud pipeline reacts **and** an
  audit logger reacts **and** a metrics counter reacts.

### Pattern B — Queue / work-queue: *exactly one* worker gets it

A message goes to a queue; a **pool of identical workers** shares the load —
each message is handled by **one** of them.

```
                        ┌─▶ Worker 1 ┐
Producer ─[queue]──────▶├─▶ Worker 2 ├─ each MESSAGE handled by exactly ONE worker
                        └─▶ Worker 3 ┘
```

- **Use when:** you have work to distribute across copies of the *same* service
  for scale. E.g., 30 copies of rule-011 sharing the incoming rule messages.
- **This is the load-balancing pattern** that makes stateless horizontal scaling
  ([1.4](../01-foundations/1.4-state-the-hard-problem.md)) actually work.

### Pattern C — Streaming / log: messages are *retained* and replayable

Messages are appended to a durable **log** and kept. Consumers track their own
position and can **replay** from any point.

```
Producer ─▶ [ ...msg8 msg9 msg10... ] (durable, ordered, retained)
                    ▲            ▲
              consumer A    consumer B   (each at its own offset, can rewind)
```

- **Use when:** you need durability, replay, ordering, or event-sourcing. Kafka
  is the archetype; **NATS JetStream** (what Tazama uses) adds this
  streaming/persistence layer on top of plain NATS pub-sub.

**Tazama uses a blend:** NATS gives it pub-sub *addressing* (subjects), JetStream
gives it *durability + queue-group load-sharing*. That's how one system gets
fan-out (Pattern A, Event Director → rules), work-sharing (Pattern B, N copies of
a rule), and failure-safe retention (Pattern C, messages survive a crash) — all
from one bus. Next lesson goes deep on exactly how.

## A decision cheat-sheet

Ask these when choosing:


| Question                                               | Lean synchronous (HTTP) | Lean asynchronous (bus) |
| ------------------------------------------------------ | ----------------------- | ----------------------- |
| Does the caller need the answer to proceed*right now*? | Yes                     | No                      |
| Must producer & consumer be up at the same instant?    | Acceptable              | No — decouple them     |
| Do I need to absorb bursts / failures?                 | No                      | Yes                     |
| Do I need to fan out to many consumers?                | No                      | Yes (pub-sub)           |
| Do I need to scale one consumer to many copies?        | (needs a load balancer) | Yes (queue group)       |
| Do I need replay / audit / ordering?                   | No                      | Yes (streaming/log)     |

## The cost of async you must respect

Async isn't free — it buys resilience with **complexity**:

- **No inline answer** — results arrive as *other* messages; you must design the
  return path.
- **Ordering** isn't guaranteed unless you arrange it — messages can arrive out
  of order.
- **Duplicates happen** — "at-least-once" delivery means you need idempotency
  ([1.4](../01-foundations/1.4-state-the-hard-problem.md)).
- **Debugging is harder** — the flow is spread across the bus, so you *need*
  tracing (Module 6.2). Remember the `traceParent` Tazama threads through? That's
  the answer to "how do I follow one transaction across all these async hops?"
