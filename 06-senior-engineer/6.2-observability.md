# 6.2 — Observability: logs, metrics, traces

## Why this is a senior skill, not a footnote

In a monolith, when something breaks you attach a debugger. In a distributed
system like Tazama, the bug's **cause** and its **symptom** are in **different
processes on different machines**, connected by async messages. You can't step
through it. Your *only* window into what happened is the **telemetry the system
emits**. So a senior engineer treats observability as a **first-class design
concern**, not something bolted on after an outage.

> **Observability** = can you answer "what is the system doing, and why did *this*
> request behave that way?" *without* deploying new code to find out?

Tazama takes this so seriously it has an entire
[`../../Technical/Logging/`](https://github.com/tazama-lf/docs/blob/main/Technical/Logging/) documentation section and a
custom logging framework. That's a mature signal.

---

## The three pillars

Every observability discussion comes down to three complementary data types.
Learn what each answers.

### 1. Logs — "what happened, in detail, at this point"

Timestamped records of events. "Received transaction X." "Rule 011 exited with
`.x01` (insufficient history)." "Failed to send to Typology Processor."

The senior upgrade: **structured logging.** Instead of free-text strings, emit
**machine-parseable** records (JSON) with consistent fields — a level, a message,
a **correlation id**, a service name. Tazama uses **`pino`** (a fast structured
JSON logger) via `frms-coe-lib`'s `LoggerService`, and its log signature carries
an **id** so logs can be tied to a specific transaction:

```ts
// frms-coe-lib logger signature (conceptually)
logger.log(message, serviceOperation?, id?, callback?)
//                                     ^^^ the correlation id — the key to it all
```

Why structured + id matters: with 10 services logging thousands of lines a
second, "grep the text" doesn't scale. But "show me every log line where
`id = this transaction`, across all services, in order" **reconstructs one
transaction's whole journey** — *if* every service stamps the same id. That id is
the thread that stitches a distributed story back together.

### 2. Metrics — "how much / how many / how fast, over time"

Aggregated numbers over time: transactions per second, p99 latency, error rate,
queue depth, CPU. Logs are per-event; **metrics are the trends.** They answer
"is the system healthy *right now*?" and "is it getting worse?" — and they're
what you **alert** on (Tazama's Helm charts include **Prometheus + Grafana** for
exactly this: Prometheus scrapes metrics, Grafana graphs them).

Remember `prcgTm` (processing time) that the rule-executer records on every
`RuleResult` ([2.2](../02-tazama-architecture/2.2-transaction-journey.md))? That's
a metric being emitted from the hot path so you can watch rule latency
([1.2](../01-foundations/1.2-latency-throughput-numbers.md)) — measure the p99,
not the average.

The classic metrics to watch are the **"RED"** trio per service: **R**ate
(requests/sec), **E**rrors (failures/sec), **D**uration (latency distribution).
If you only had three graphs per service, these are them.

### 3. Traces — "follow one request across all services"

This is the distributed-systems superpower. A **trace** follows a **single
transaction** as it hops TMS → Event Director → rule → typology → …, showing how
long it spent in each and where it slowed or failed.

You already saw the mechanism! In [2.2](../02-tazama-architecture/2.2-transaction-journey.md),
the Event Director puts `traceParent: apm.getCurrentTraceparent()` into the
message metadata. That `traceParent` is a **trace id** propagated across every
hop, so **Elastic APM** (which Tazama uses — `frms-coe-lib/src/services/apm.ts`)
can assemble the full cross-service timeline of one transaction. When someone
asks "why was *this* payment slow?", the trace shows you *exactly* which hop —
without guessing.

```
Trace of one transaction:
 TMS         ▓▓ 4ms
 EventDir      ▓▓▓ 6ms
 rule-011         ▓▓▓▓▓▓▓▓▓▓▓▓ 55ms   ← there's your slow hop
 rule-074         ▓▓▓ 7ms
 Typology                     ▓▓▓▓ 9ms
```

## How they work together (the real workflow)

An outage/investigation flows through all three:

1. A **metric alert** fires: "error rate on rule-011 jumped, p99 doubled." (You
   learn *that* something's wrong.)
2. You look at **traces** for slow/failed transactions: "they're all stalling at
   the rule-011 → typology hop." (You learn *where*.)
3. You read the **logs** for those specific transaction ids: "insufficient DB
   connections, query timing out." (You learn *why*.)

Metrics tell you **something** is wrong; traces tell you **where**; logs tell you
**why**. A system missing any pillar leaves you blind at that step. This is why
seniors insist on all three *before* the outage, not during it.

## Tazama's observability stack (name-recognition)

You'll see these across the repos — now you know what each is for:

- **pino** — structured JSON logging (in-code).
- **Elastic APM** — distributed tracing + performance (the `traceParent` end).
- **ELK / OpenSearch** (Elasticsearch, Logstash, Kibana) — collect, store, and
  **search** logs at scale; dashboards.
- **Prometheus + Grafana** — metrics scraping + dashboards + alerting (Helm
  charts).
- **NATS sidecar → Lumberjack** — Tazama's own pattern where each processor's
  **sidecar** ships logs over NATS to a central "Lumberjack" collector
  ([3.2](../03-messaging-and-data/3.2-nats-deep-dive.md)). A clever reuse of the
  message bus for telemetry plumbing.

---

## The design lesson: build for observability up front

The senior takeaway isn't "install Grafana." It's that **observability is a
design property you bake in**:

- Propagate a **correlation/trace id** through every hop from the start (Tazama
  does — `id` in logs, `traceParent` in messages). Retrofitting this later is
  painful.
- Emit **structured** logs and **metrics** from the hot path deliberately
  (`prcgTm`).
- Decide **what "healthy" means** as numbers (SLOs — [6.4](6.4-reliability-and-slos.md))
  so alerts are meaningful.

A system you can't observe is a system you can't operate. And "can we operate
it?" is the question that separates a demo from production.
