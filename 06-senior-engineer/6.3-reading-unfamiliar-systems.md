# 6.3 — Reading a system you didn't build

This is the single most-used senior skill and the least-taught. You will spend
far more of your career **understanding existing systems** than building new
ones. The good news: it's a *method*, and you just practiced it on Tazama.

## Why this skill is the multiplier

A senior engineer is dropped into an unfamiliar codebase and, within a day or
two, can say "here's the shape, here's where the risk is, here's where your
change should go." That's not magic or memory — it's a **repeatable process** for
turning an intimidating pile of files into a mental model. Let's name the process
you've been using.

---

## The method (the order matters)

### Step 1 — Find the edges (inputs and outputs) first

Never start by reading random files top to bottom. Start at the **boundaries**:
what comes *in*, what goes *out*? ([1.1](../01-foundations/1.1-what-is-system-design.md),
question 1.) For Tazama you found: **in** = an HTTP POST of an ISO 20022
transaction; **out** = an alert to a case-management system. Two facts, and
suddenly the whole thing has a direction.

*How to find edges fast:* look for HTTP controllers/routes, message
consumers/producers, and the README's "what is this" paragraph. In Tazama:
`server.init(...)` (consumers) and `handleResponse(..., [subjects])` (producers).

### Step 2 — Trace one request end to end

Pick **one** representative flow and follow it through every hop, exactly like
[2.2](../02-tazama-architecture/2.2-transaction-journey.md). Don't try to
understand everything — understand **one path** completely. That single trace
gives you the skeleton; everything else hangs off it. You now know: the number of
services, the order, the transport between them, and roughly what each does — from
*one* trace.

### Step 3 — Find the repeating pattern

Real systems repeat a skeleton (good ones do, anyway). The moment you find it,
the codebase collapses from "N services to learn" to "1 pattern + N sets of
domain logic." You found Tazama's in [2.3](../02-tazama-architecture/2.3-processor-pattern.md):
every processor is `config → logger → DB managers → server.init(handler) →
handleResponse`. After that, opening a new service is a 3-lookup job, not a
research project. **Always hunt for the repeating skeleton early** — it's the
biggest leverage in the whole method.

### Step 4 — Locate the state

Where does data live? ([1.1](../01-foundations/1.1-what-is-system-design.md),
question 3.) Find the database managers / connection configs. For Tazama:
PostgreSQL (history/config), Redis/Valkey (cache), plus CouchDB/OpenSearch in
CMS. Knowing where state lives tells you where the *truth* is and where the *hard
problems* ([1.4](../01-foundations/1.4-state-the-hard-problem.md)) are
concentrated.

### Step 5 — Read the contracts (the shared types)

The **shared interfaces** are the system's grammar. Tazama's `frms-coe-lib`
interfaces (`NetworkMap`, `RuleResult`, `DataCache`, `Pacs002`) told you the
domain model *without* reading business logic
([2.4](../02-tazama-architecture/2.4-rules-typologies-scoring.md)). Types are the
fastest way to learn what a system is *about*. Read them before the logic.

### Step 6 — Note what's said vs what's true

Docs drift from code. You saw it repeatedly: docs/older charts say **ArangoDB**;
current code runs **PostgreSQL**. READMEs call NATS a "message queue"; it's really
pub-sub/JetStream. **The code is ground truth; docs are a historical hint.** A
senior engineer holds both and notices the gap — that gap often *is* the story
(a half-finished migration, a deprecated path). Being able to say "the docs
describe the old world" is a senior-level read of a codebase.

## The tools of the trade (mechanical, but essential)

To execute the method fast, you lean on:

- **`grep` / ripgrep** — search for a subject string, a function name, an env
  var across the whole tree. ("Who publishes to `event-director`?" → grep it.)
- **Follow the config** — env vars and `.env` files are a map of what connects to
  what. Reading `env/tms-service.env` told you its cache, DB, and identity in ten
  lines ([4.5](../04-devops-networking/4.5-configuration-and-secrets.md)).
- **Read the entry point** — `index.ts` / `main.ts` / `main.py`. The wiring lives
  there; the `server.init(...)` line reveals a service's place in the pipeline.
- **Read tests** — tests show *intended* behavior and usage examples, often
  clearer than the code. (Tazama tracks unit-test coverage:
  [`../../Technical/unit-test-coverage.md`](https://github.com/tazama-lf/docs/blob/main/Technical/unit-test-coverage.md).)
- **Draw it** — a box-and-arrow sketch as you go. If you can't draw it, you don't
  understand it yet. (Tazama even has a [drawio guide](https://github.com/tazama-lf/docs/blob/main/Guides/drawio-guide.md).)

---

## What NOT to do

- **Don't read files alphabetically or top-to-bottom.** You'll drown. Follow the
  *flow*, not the *filesystem*.
- **Don't try to understand everything before doing anything.** Understand the
  one path your task touches; expand only as needed.
- **Don't trust docs over code** when they conflict.
- **Don't skip the entry point and shared types** to dive into business logic —
  you'll miss the map and get lost in a corner.

## You already did this

Everything in Modules 1–4 was this method executed on Tazama: edges → trace →
pattern → state → contracts → doc/code gaps. That's *why* the curriculum is
ordered the way it is — it's not just teaching Tazama, it's **demonstrating the
method you'll use on every future system.** Next time you're dropped into an
unknown codebase, run these six steps in order. It works on anything.

## Go look at it (a real exercise)

Pick a Tazama service you have **not** opened yet — say `admin-service` or
`event-flow` (in `/home/sohaib/Documents/frms/`). Apply the method in 30 minutes:

1. README + entry point → what are its edges?
2. Find its `server.init(...)` → what subjects does it consume/produce?
3. Find its DB-manager config → what state does it touch?
4. Does it follow the processor skeleton? (It should.)
5. One line: what's this service's *one job*?

If you can answer #5 in a sentence after 30 minutes, the method works — and it
always will.
