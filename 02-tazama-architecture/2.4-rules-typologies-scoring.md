# 2.4 — Rules, Typologies & Scoring (the domain logic)

This lesson is about *what Tazama actually decides* and how the decision is
built up from tiny pieces. It's a masterclass in a senior-engineering idea:
**compose a complex judgment out of small, independently-testable units.**

## The three levels of the hierarchy

```
Network Map
  └─ Message (a transaction type, e.g. pacs.008)
       └─ Typology  (a named fraud/AML scenario, e.g. "Phishing scam")
            └─ Rule  (one narrow question, e.g. "is the amount unusually large?")
```

This is encoded *exactly* in a real TypeScript interface — this is the spine of
the whole domain:

```ts
// frms-coe-lib/src/interfaces/NetworkMap.ts
export interface Rule     { id: string; cfg: string; }
export interface Typology { id: string; cfg: string; rules: Rule[]; }
export interface Message  { id: string; cfg: string; txTp: string; typologies: Typology[]; }
export interface NetworkMap { active: boolean; cfg: string; tenantId: string; messages: Message[]; }
```

Read it bottom-up: a **NetworkMap** is a per-tenant config saying "for message
type X, evaluate typologies A, B, C; typology A is made of rules 011, 074, …".
**The network map is the configuration that wires the whole pipeline** — and
it's *data*, not code, so you can change what Tazama checks without redeploying.
That's a big deal (see the end of this lesson).

## A RULE: one question, one answer

A rule answers **one** narrow question about a transaction and its history. From
the README's example of a phishing scam, three separate rules might be:

- Age of the account/participant
- Value of the transaction
- Whether there's a prior relationship with the recipient

Each is a **rule**. None of them decides "this is fraud" — each just reports its
own small finding. The judgment comes from combining them (the typology).

### The rule contract (what you'd write to add a rule)

Every rule is a package that exports **exactly one function**, `handleTransaction`:

```ts
// rule-011/src/rule-011.ts  (identical signature in rule-template, rule-074)
export async function handleTransaction(
  req: RuleRequest,          // { transaction, networkMap, DataCache, metaData? }
  determineOutcome: (value: number, ruleConfig: RuleConfig, ruleResult: RuleResult) => RuleResult,
  ruleRes: RuleResult,       // pre-seeded result to fill in and return
  _loggerService: LoggerService,
  ruleConfig: RuleConfig,    // per-tenant tunables: parameters, bands, exitConditions
  databaseManager: DatabaseManagerInstance<RuleExecutorConfig>,  // scoped DB access
): Promise<RuleResult>
```

The elegant part: a rule's job is to **compute a single number** and hand it to
the injected `determineOutcome`, which maps that number into a **band**:

```ts
// rule-011/src/rule-011.ts (end of the happy path)
ruleRes = determineOutcome(currentInterval, normalizedRuleConfig, ruleRes);
return ruleRes;
```

So the division of labor is:

- **The rule author** writes only the domain math (compute one value).
- **The band config** (`ruleConfig.bands`, e.g. `{ lowerLimit, upperLimit,
  subRuleRef, reason }`) — supplied per tenant as *data* — decides which
  category that value falls into.

This means the **same rule code behaves differently per tenant** just by
changing config. Bank A can flag transactions over $10k; Bank B over $50k;
**same code, different bands.** That's configuration-driven design, and it's why
Tazama can serve many institutions without forking.

### Two real rules, to make it concrete

- **rule-011** computes a *statistic over history*: it builds a histogram of
  successful transactions to the creditor per time interval, computes an average
  and standard deviation, and checks where the current interval falls (bands are
  rescaled as `limit * stdDev + avg`). It queries PostgreSQL event-history with
  a **named prepared statement** (fast, safe from SQL injection —
  [Module 3.3](../03-messaging-and-data/3.3-databases.md)).
- **rule-074** computes a *geographic distance*: the **haversine distance**
  between two transaction locations. Big distance in short time → suspicious
  ("impossible travel").

Same skeleton, completely different question. That's the point.

### What a rule returns

```ts
// frms-coe-lib/src/interfaces/rule/RuleResult.ts
export interface RuleResult {
  id: string; cfg: string; subRuleRef: string; tenantId: string;
  indpdntVarbl: number;    // the raw computed value
  reason?: string; prcgTm?: number;
  wght?: number;           // the weight — used LATER, by the typology processor
}
```

A rule emits a **category** (`subRuleRef`, e.g. `.x01`, `.x03`) plus the **raw
number** (`indpdntVarbl`). It does **not** score. Note `wght` — the rule doesn't
set the final weighting; that's the next level's job.

### Rules fail gracefully, on purpose

Real rules spend a lot of code on **exit conditions** — degenerate cases where
the answer is "can't meaningfully evaluate": transaction unsuccessful (`.x00`),
not enough history (`.x01`), no variance in the data (`.x03/.x04`). Each returns
a specific `subRuleRef` early. This is [1.5](../01-foundations/1.5-design-for-failure.md)
**graceful degradation** at the smallest scale — the rule always returns a valid,
categorized result rather than throwing. Tazama even documents these:
[`../../Technical/Processors/Rule-Processors/standard-rule-processor-exit-and-error-conditions.md`](https://github.com/tazama-lf/docs/blob/main/Technical/Processors/Rule-Processors/standard-rule-processor-exit-and-error-conditions.md).

## A TYPOLOGY: combining rules into a scenario

A **typology** is a named fraud/AML scenario (e.g. "Phishing Scam", "Layering")
defined as a **weighted set of rules**. The **Typology Processor** (downstream
service) collects the `RuleResult`s for a typology and combines them — each
rule's outcome contributes according to its **weight** — into a single
**typology score**.

Why weight? Because not all signals are equal. "Recipient is brand new" might
matter more than "amount is slightly above average." Weights let domain experts
tune the scenario without touching rule code. Again: **judgment lives in
config/weights, mechanics live in code.**

> **Where this code lives:** the Typology Processor is a separate service not
> fully in this checkout. We know it's the next hop because the rule-executer's
> code literally logs *"send.to.typroc"* / *"Failed to send to Typology
> Processor"*. Teach it as "downstream of the rule executer," which is exactly
> what the code tells us.

## SCORING & INTERDICTION: the decision

Finally, **TADProc** (Transaction Aggregation & Decisioning Processor) takes the
typology scores and applies **thresholds**:

- Below threshold → allow, no alert.
- Above alert threshold → raise an **alert** to Case Management.
- Above interdiction threshold → **block** the transaction in real time.

The **Event Flow (EFRuP)** feature can **override** a block under configured
conditions, and supports operational controls like non-overridable blocks for
specific accounts.

Notice the funnel of responsibility, and why it's good design:

```
many Rules (compute) → few Typologies (combine + weight) → one Decider (threshold + act)
   narrow & testable       domain scenarios                  the risky money-moving call
```

The **dangerous** part — "should we block real money?" — is isolated in **one**
place with clear thresholds, not scattered across 50 rules. That's cohesion
([1.3](../01-foundations/1.3-coupling-and-services.md)) protecting you where it
matters most.

## The senior takeaway: data-driven behavior

Step back. What's actually configurable *without a code deploy*?

- **Which** rules/typologies run (the network map).
- **How** each rule bands its result (rule config bands, per tenant).
- **How** rules combine (typology weights).
- **When** to alert/block (thresholds).

All of that is **data**, loaded from PostgreSQL and cached in Redis. The **code**
is just the mechanism. This separation — *policy in data, mechanism in code* —
is one of the highest-leverage patterns in system design. It's why a Tazama
operator can respond to a new fraud pattern by changing config, not by shipping
a release. When you design systems, always ask: **"what will need to change
often, and can I make that a config value instead of code?"**
