# 2.3 — The processor pattern (every Tazama service, same skeleton)

## Why this lesson matters most for *reading* the code

Here's the trick that makes Tazama learnable: **almost every service is the same
program with different logic plugged in.** They all use `frms-coe-startup-lib`
to consume from NATS, run a handler, and produce to NATS. Learn this one
skeleton and you can open *any* Tazama processor and immediately know where to
look.

The skeleton:

```
1. Load & validate config from env vars.
2. Create a logger.
3. Create database managers (only for the stores this service needs).
4. server = new StartupFactory()   // picks NATS or JetStream from env
5. server.init(myHandler, logger, [consumeSubjects], produceSubject)
6. Inside myHandler: do the work, then server.handleResponse(result, [subjects])
```

That's it. Every processor. Let's break down the two calls that matter.

---

## `server.init(handler, …)` — how a service *consumes*

`StartupFactory` reads an env var (`SERVER_TYPE`) and gives you a NATS or
JetStream client — **the service code never hard-codes which**. That's Tazama's
design principle "abstract third-party tools so you can swap them"
([1.3](../01-foundations/1.3-coupling-and-services.md)) made concrete:

```ts
// frms-coe-startup-lib/src/services/startupFactory.ts
constructor() {
  switch (startupConfig.startupType) {
    case 'jetstream': this.startupService = new JetstreamService(); break;
    case 'nats':      this.startupService = new NatsService();      break;
  }
}
```

`init` connects, subscribes to your consume-subjects, and runs a **loop**. For
every message it calls *your* handler, handing it the decoded message and a
"reply" continuation, then **acks** the message:

```ts
// frms-coe-startup-lib/src/services/jetstreamService.ts (the consume loop)
for await (const message of sub) {
  const request = message.json<string>();
  onMessage(request, (msg) => { void this.handleResponse(msg); });
  message.ack();   // tell JetStream "I've got it" — the failure-safety knob
}
```

That `message.ack()` is a [1.5](../01-foundations/1.5-design-for-failure.md)
detail worth pausing on: JetStream holds the message until you ack. If the
service crashes **before** ack, the message is redelivered — the work isn't lost.
This is the durable-bus failure absorption you learned about, in one line.

---

## `server.handleResponse(payload, [subjects])` — how a service *produces*

To pass work downstream, a handler calls `handleResponse`. It **protobuf-encodes**
the payload (compact, fast — [1.2](../01-foundations/1.2-latency-throughput-numbers.md))
and publishes it to this service's own producer stream **plus** any extra
subjects you name:

```ts
// jetstreamService.ts (the produce path, abridged)
async handleResponse(response, subject?) {
  const res = ...encode(response);
  publishes.push(this.js.publish(this.producerStreamName, sc.encode(res)));
  if (subject) for (const sub of subject) publishes.push(this.js.publish(sub, sc.encode(res)));
  await Promise.all(publishes);
}
```

This is why in [2.2](2.2-transaction-journey.md) you saw the Event Director do
`server.handleResponse(toSend, ['sub-rule-011'])` — it's naming the extra subject
to fan out to. **The `[subjects]` argument is the routing knob.**

## The interface every service implements

There's a single interface that defines the whole contract:

```ts
// frms-coe-startup-lib/src/interfaces/iStartupService.ts
export interface IStartupService {
  init: (onMessage, loggerService?, parConsumerStreamNames?, parProducerStreamName?) => Promise<boolean>;
  initProducer: (loggerService?, parProducerStreamName?) => Promise<boolean>;
  handleResponse: (response: object, subject?: string[]) => Promise<void>;
}
```

Three methods. That's the entire messaging surface a Tazama service touches.
**This is excellent design** — a tiny, stable interface hides all the NATS
complexity. When you build your own systems, aim for interfaces this small.

---

## Databases are composed à la carte

The other half of the skeleton is data access. `frms-coe-lib`'s
`CreateDatabaseManager(config)` gives a service **only the stores it declares** —
and TypeScript enforces it, so a service that didn't ask for `eventHistory`
literally can't call `._eventHistory`:

```ts
// frms-coe-lib/src/services/dbManager.ts
type DatabaseManagerInstance<T> = ManagerStatus &
  (T extends { eventHistory: DBConfig } ? EventHistoryDB : Record<string, unknown>) &
  (T extends { rawHistory:  DBConfig } ? RawHistoryDB  : Record<string, unknown>) &
  ...
  (T extends { redisConfig: RedisConfig } ? RedisService : Record<string, unknown>);
```

This is **least-privilege via the type system** — a service can't accidentally
depend on a store it shouldn't touch. A subtle but senior-grade design choice:
the *types* encode the architecture's boundaries.

> **Version caveat (real-world gap to notice):** the rule-executer actually
> imports a newer `CreateStorageManager` + a `Database.*` enum, while the lib's
> public index still exports the older `CreateDatabaseManager`. Two generations
> of the same API coexist in the checkout. This is normal migration debris —
> and spotting it is exactly the "docs/code drift" skill from
> [2.1](2.1-birds-eye-view.md).

## Putting the whole skeleton together (rule-executer, annotated)

```ts
// rule-executer/src/index.ts — the canonical processor bootstrap
const configuration = validateProcessorConfig(extraEnvVars);   // 1. config from env
const loggerService = new LoggerService(configuration);        // 2. logger
await initializeDB();  // 3. CreateStorageManager([CONFIGURATION, EVENT_HISTORY, RAW_HISTORY, LOCAL])
const server = new StartupFactory();                           // 4. transport (NATS/JetStream)
await server.init(                                             // 5. consume + declare producer
  execute, loggerService,
  [`sub-rule-${cfg.RULE_NAME}@${cfg.RULE_VERSION}`],           //    consume subject
  `pub-rule-${cfg.RULE_NAME}@${cfg.RULE_VERSION}`,             //    produce subject
);
// + Node `cluster`: fork one worker per CPU to use all cores  (6. scale-out within the box)
```

That step 6 is a nice bonus: each service uses Node's `cluster` to fork a worker
**per CPU core**, so a single container already uses the whole machine before you
even scale to multiple containers. Two layers of scaling: threads within a box,
copies across boxes.

---

## Why this pattern is the real lesson

Once you see it, the whole platform decodes:

- **To understand any service**, find its `server.init(...)` call → that tells
  you what it **consumes** and **produces**. You now know its place in the
  pipeline without reading the whole thing.
- **To understand its logic**, read the handler passed as the first arg to
  `init` (e.g. `handleTransaction`, `execute`, `handleMessage`).
- **To understand its data**, find its `CreateDatabaseManager` / `CreateStorageManager`
  config → that lists exactly which stores it touches.

Three lookups and you've mapped a service. That's the payoff of a **consistent
pattern** across a codebase — and a lesson for your own work: *make your
services boringly similar; save the creativity for the domain logic.*
