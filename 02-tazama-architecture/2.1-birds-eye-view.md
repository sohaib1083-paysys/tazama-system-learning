## What Tazama is, in one paragraph

Tazama is an **open-source, real-time transaction monitoring system** for
detecting fraud and money laundering. A financial institution sends it a payment
(as an ISO 20022 message). Tazama runs a set of **rules** against that payment
and the sender/receiver's history, groups the rule outcomes into **typologies**
(named fraud/AML scenarios), scores them, and if the evidence is strong enough,
raises an **alert** to a case-management system — and can even **block** the
transaction in real time. It's built to run from a few transactions a day up to
**3,000+ per second**.

Now let's see the shape.

## The pipeline (the one diagram to memorize)

```
                         HTTP POST (ISO 20022 txn)
                                  │
                                  ▼
                ┌─────────────────────────────────┐
                │  TMS / Event Monitoring Service  │  validate, normalize,
                │        (the "front door")        │  persist, then publish
                └─────────────────────────────────┘
                                  │  NATS subject: "event-director"
                                  ▼
                ┌─────────────────────────────────┐
                │          Event Director          │  look up the network map,
                │          (the "router")          │  fan out to applicable rules
                └─────────────────────────────────┘
                        │        │        │  NATS subjects: "sub-rule-<id>"
             ┌──────────┘        │        └──────────┐   (one message per rule)
             ▼                   ▼                   ▼
      ┌────────────┐      ┌────────────┐      ┌────────────┐
      │ Rule Exec  │      │ Rule Exec  │      │ Rule Exec  │   each runs ONE rule,
      │  (rule-011)│      │  (rule-074)│      │  (rule-901)│   emits a RuleResult
      └────────────┘      └────────────┘      └────────────┘
             │                   │                   │  NATS: "pub-rule-<name>@<ver>"
             └──────────┬────────┴─────────┬─────────┘
                        ▼                  ▼
                ┌─────────────────────────────────┐
                │        Typology Processor        │  weight + combine rule
                │        (the "scorer")            │  results into typology scores
                └─────────────────────────────────┘
                                  │  NATS
                                  ▼
                ┌─────────────────────────────────┐
                │  TADProc + Event Flow / Adjud.   │  aggregate, apply thresholds,
                │       (the "decider")            │  decide block / allow / alert
                └─────────────────────────────────┘
                                  │  NATS
                                  ▼
                ┌─────────────────────────────────┐
                │      Case Management System      │  humans investigate alerts
                └─────────────────────────────────┘
```

Read this diagram through the Module 1 lens:

- It's a **pipeline of stateless services** ([1.4](../01-foundations/1.4-state-the-hard-problem.md))
  connected by a **message bus**, not HTTP calls ([1.3](../01-foundations/1.3-coupling-and-services.md)).
- The **fan-out at the Event Director** is how rules scale independently
  ([1.2](../01-foundations/1.2-latency-throughput-numbers.md)) — hot rules just
  get more copies on the same subject.
- The message bus makes each hop **failure-absorbing** ([1.5](../01-foundations/1.5-design-for-failure.md)).

Everything in this module is just zooming into boxes of this diagram.

## The supporting cast (the infrastructure)

The services above don't work alone. Around them sit shared infrastructure —
this is the stuff you said you want to understand, and Module 4 covers it deeply.
For now, just the roles:

| Component | Role | Module 1 concept |
|---|---|---|
| **NATS (JetStream)** | The message bus — every arrow in the diagram. Durable pub-sub. | Loose coupling, failure absorption |
| **PostgreSQL** | Durable state: transaction history, event history, configuration. | Stateful store |
| **Redis / Valkey** | Fast in-memory cache: network map, hot lookups. | Caching, latency |
| **Keycloak** | Identity/auth — who's allowed to send transactions. | Security boundary |
| **Elastic APM / ELK** | Observability — logs, traces, metrics. | Module 6.2 |

> **Important honesty note for you specifically:** Tazama's docs and older
> deployments describe **ArangoDB** as the database, and the older **Helm
> charts** deploy ArangoDB. The **current** running services (in the
> `tazama-stack` docker-compose) use **PostgreSQL** and **Valkey** (a Redis
> fork) instead. So you'll see both in the repos. When a lesson says "the
> database," I mean the durable store — Postgres today, Arango in the older
> stack. I'll flag it wherever it matters. This kind of "docs describe the old
> world, code is the new world" gap is *extremely normal* in real systems and
> learning to spot it is itself a senior skill.

## The two shared libraries (the glue)

Two libraries make every service look and behave the same — this is a big reason
the codebase is learnable:

- **`frms-coe-lib`** — the shared core. Database managers, the Redis client, the
  logger, config loading, and the **TypeScript interfaces** that define every
  message shape (`Pacs002`, `NetworkMap`, `RuleResult`, `DataCache`). These
  interfaces *are* the contracts between services ([1.3](../01-foundations/1.3-coupling-and-services.md)).
- **`frms-coe-startup-lib`** — the messaging bootstrap. It gives every service
  the same `server.init(handler, …)` (to consume) and `server.handleResponse(payload, [subjects])`
  (to produce) pattern. **Learn this one pattern and you can read every Tazama
  service**, because they're all built on it. That's the subject of
  [2.3](2.3-processor-pattern.md).
