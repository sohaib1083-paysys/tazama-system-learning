# 2.2 — The transaction journey (follow one payment through every service)

This is the most important lesson in the module. We follow **one transaction**
from the moment it arrives to the moment an investigator sees an alert, naming
the **exact NATS subjects** and **exact files** at each hop. Open the files.

Our example: a `pacs.008` (a credit transfer) arrives, followed by its
`pacs.002` (payment status). Tazama scores it.

---

## Hop 0 → 1: The client calls the front door (HTTP)

**Where:** Event Monitoring Service (a.k.a. DEMS / the TMS API).
**Repo:** `/home/sohaib/Documents/frms/event-monitoring-service`

The client sends an HTTP `POST`:

```
POST /dems-engine/tenant01,pacs,008,001,10
Authorization: Bearer <JWT>
Content-Type: application/json   (or XML)
{ ...the ISO 20022 transaction... }
```

- The URL path encodes the **tenant** and the **message type** (`pacs.008.001.10`).
- A `TazamaAuthGuard` checks the **JWT** — this is the security boundary
  (Keycloak issued that token). Unauthenticated → rejected here.
- **Controller:** [`event-monitoring-service/src/dems-engine/dems-engine.controller.ts`](../../../event-monitoring-service/src/dems-engine/dems-engine.controller.ts)
- The service **validates** the payload against a JSON Schema, **transforms**
  XML→JSON if needed, applies configured **field mappings**, and builds the
  canonical Tazama payload: `{ transaction, DataCache }`.

Why a normalize step at the front? So *every downstream service* sees one
consistent shape, regardless of what messy format the bank sent. This is the
**anti-corruption layer** pattern — quarantine the outside world's mess at the
edge. (This mapping/normalization toolkit lives in `tcs-lib`.)

Then it does two things **in parallel** — note the design choice:

```ts
// dems-engine.service.ts  saveTransactionDataAndNotify()
const results = await Promise.allSettled([
  this.databaseOperationsService.saveTransactionHistory(tazamaPayload, ...), // persist
  this.natsService.notifyEventDirector(tazamaPayload),                       // publish
]);
```

- `Promise.allSettled` (not `all`) → *one failing doesn't reject the other*.
  A [1.5](../01-foundations/1.5-design-for-failure.md) failure-design choice.
- It **persists to PostgreSQL** (transaction history) **and publishes to NATS**.

**Publishes to NATS subject: `event-director`** (env: `PRODUCER_STREAM=event-director`).

## Hop 1 → 2: The router decides which rules apply

**Where:** Event Director. **Repo:** `/home/sohaib/Documents/frms/event-director`

- **Consumes** NATS subject `event-director` (env: `CONSUMER_STREAM=event-director`).
- **Entry:** [`event-director/src/index.ts`](../../../event-director/src/index.ts)
  — literally `server.init(handleTransaction)`.
- **Core logic:** [`event-director/src/services/logic.service.ts`](../../../event-director/src/services/logic.service.ts)

What it does — this is the "router" job:

1. Loads the active **network map** for this tenant + transaction type. The cache
   key is `${tenantId}:${txTp}` — **multi-tenant** and **cached** (Redis +
   in-process `node-cache`) so it isn't hitting the DB on every transaction.
   ([1.2](../01-foundations/1.2-latency-throughput-numbers.md) latency thinking.)
2. **Prunes** the network map to just the rules relevant to *this* message type.
3. **Deduplicates** rules (the same rule can appear under multiple typologies;
   run it once) by `id` + `cfg`.
4. **Fans out** — publishes one message *per applicable rule*:

```ts
// logic.service.ts  sendRuleToRuleProcessor()
const toSend = { transaction: req, networkMap, DataCache: dataCache,
  metaData: { ...metaData, traceParent: apm.getCurrentTraceparent() } };
await server.handleResponse(toSend, [`sub-rule-${rule.id}`]);   // one per rule
```

**Publishes to NATS subjects: `sub-rule-<ruleId>`** — one message each.

> This fan-out is the scaling pivot. If rule-011 is expensive, run 30 copies
> subscribed to `sub-rule-011@…`; they share the load. The Event Director
> neither knows nor cares how many there are. Re-read
> [1.3](../01-foundations/1.3-coupling-and-services.md) if this doesn't feel
> magical yet — it should.

Notice also `traceParent` in the metadata — that's a **distributed trace ID**
being threaded through so you can later follow one transaction across all
services in APM. (Module 6.2.)

## Hop 2 → 3: A rule runs

**Where:** Rule Executer (one deployment per rule).
**Repo:** `/home/sohaib/Documents/frms/rule-executer`

- **Consumes** `sub-rule-<RULE_NAME>@<RULE_VERSION>` (set per deployment via
  `rule-011.env`, `rule-074.env`, …).
- **Produces** to `pub-rule-<RULE_NAME>@<RULE_VERSION>`.
- **Entry:** [`rule-executer/src/index.ts`](../../../rule-executer/src/index.ts) —
  the best "read first" file. It sets up the DB managers, the logger, then:

```ts
// rule-executer/src/index.ts  runServer()
await server.init(
  execute, loggerService,
  [`sub-rule-${configuration.RULE_NAME}@${configuration.RULE_VERSION}`],  // consume
  `pub-rule-${configuration.RULE_NAME}@${configuration.RULE_VERSION}`,    // produce
);
```

The `execute` controller ([`rule-executer/src/controllers/execute.ts`](../../../rule-executer/src/controllers/execute.ts)):

1. Validates the request.
2. Finds this rule's `cfg` by walking the network map hierarchy
   (`networkMap → messages → typologies → rules`).
3. Fetches the rule's tunable config from PostgreSQL: `databaseManager.getRuleConfig(...)`.
4. Calls the actual rule logic — imported generically as `from 'rule/lib'`, so
   **one host binary can run *any* rule package** (the rule is installed as an
   npm package aliased `rule`). Clever: the executer is generic; the rule is
   swappable.
5. Records processing time `prcgTm`, wraps everything in APM spans.
6. Publishes the result:

```ts
// execute.ts (end of happy path)
await server.handleResponse({ ...request, ruleResult: ruleRes });  // → typology processor
```

**Publishes to NATS subject: `pub-rule-<name>@<version>`** (the typology
processor's input).

(What's *inside* a rule — the `handleTransaction` contract — is
[2.4](2.4-rules-typologies-scoring.md).)

## Hop 3 → 4: Scoring and deciding

**Where:** Typology Processor, then TADProc / Event-Flow / Adjudicator.

> **Honesty note:** these services live in *other* repos not fully in this
> checkout, so I'm describing them from the contracts and code references, not
> line-by-line. The rule executer's own code literally logs *"send.to.typroc"*
> and *"Failed to send to Typology Processor"* — that's how we know the next hop.

- The **Typology Processor** collects the `RuleResult`s belonging to a typology,
  applies a **weight** (`wght`) to each rule's outcome, and combines them into a
  **typology score**.
- **TADProc** (Transaction Aggregation & Decisioning Processor) aggregates
  typology scores and applies **thresholds**: is the evidence strong enough to
  **alert**? To **block**? The **Event Flow (EFRuP)** feature can override a
  block under configured conditions.

Key idea: **a rule never decides anything.** A rule emits one categorical
outcome (`subRuleRef`) plus a raw number (`indpdntVarbl`). *Combining and
deciding* is a separate, downstream responsibility. That separation is good
design — the risky "should we block real money?" logic is concentrated in one
place, not smeared across 50 rules. (High cohesion, [1.3](../01-foundations/1.3-coupling-and-services.md).)

## Hop 4 → 5: The human sees it

**Where:** Case Management System.
**Repo:** `/home/sohaib/Documents/frms/case-management-system`

- **Consumes** NATS (subject like `relay-service-nats-tadp` /
  `investigation-service`) — turns each inbound message into an **alert**:

```ts
// case-management-system/backend/src/modules/nats/nats.service.ts
async handleMessage(req: IngestAlertDto): Promise<void> {
  const tenantId = req.transaction.TenantId || 'DEFAULT';
  await this.processAlertService.processIncomingAlert(req, 'NATS', systemId, tenantId);
}
```

- It's **dual-ingress**: NATS (to *receive* alerts) **and** an HTTP REST API +
  React UI (for *investigators* to work the cases). Different traffic, different
  door — a clean design.
- Behind it: PostgreSQL (case data), CouchDB (evidence documents), OpenSearch
  (audit logs), a BPMN workflow engine (Flowable) for case lifecycle.

The transaction's journey ends as a **case on an investigator's screen**.

## The whole journey on one line

```
HTTP POST → [event-director] → [sub-rule-<id>] → [pub-rule-<name>@<ver>]
   → typology score → aggregate/decide → alert → Case Management
```

If you can recite that, name the subjects, and point at the file for each hop,
**you understand the Tazama data plane** — which is most of understanding
Tazama.
