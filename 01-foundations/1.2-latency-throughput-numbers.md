# 1.2 — Latency, throughput & the numbers every engineer should know

## Latency vs throughput — the highway analogy

Two words people constantly confuse:

- **Latency** = how long *one car* takes to drive the highway end to end.
- **Throughput** = how many *cars per hour* pass a point on the highway.

They are **not the same** and improving one can hurt the other:

- Add more lanes (more servers) → **throughput up**, latency unchanged.
- Raise the speed limit (faster CPU) → **latency down**.
- Pack cars bumper-to-bumper (batching) → throughput up, but each car waits →
  **latency up**.

> **Tazama cares about both, differently.** It must handle **3,000+
> transactions per second** (throughput) *and* make a block/allow decision
> fast enough to be "real-time interdiction" (latency). The README and design
> principles both state these goals — go re-read them with this lens.

A concrete mental model for a request:

```
total latency = queue wait + processing time + all the network hops + DB lookups
```

In a pipeline like Tazama, a transaction's total latency is the **sum of every
stage** it passes through. That's why each stage being fast matters, and why an
extra service in the chain is never "free": it adds a hop.

## Percentiles: the average is a liar

Never trust an *average* latency. Averages hide the pain. Use **percentiles**:

- **p50** (median): half of requests are faster than this.
- **p99**: 99% are faster; the slowest 1% are worse. This is your "bad day."
- **p99.9**: the tail. At scale, this bites real users constantly.

Why it matters: if you serve 3,000 tx/s, then **1%** = 30 transactions *every
second* are hitting your p99 latency. The tail is not rare — at scale, the tail
is someone's every request. Senior engineers optimize the **p99**, not the
average.

> A system that's "10ms on average" but "2s at p99" is a system that feels
> broken to a meaningful slice of users. Always ask "what's the p99?"

## The numbers every engineer should memorize

These are the famous **"latency numbers"** (order-of-magnitude, rounded to be
memorable). Internalize the *ratios*, not the exact figures:


| Operation                       |     Time | In "human" terms (×1 billion) |
| ------------------------------- | -------: | ------------------------------ |
| L1 cache reference              |    ~1 ns | 1 second                       |
| Main memory (RAM) reference     |  ~100 ns | ~2 minutes                     |
| Read 1 MB sequentially from RAM |  ~10 µs | ~3 hours                       |
| SSD random read                 | ~100 µs | ~1.5 days                      |
| Round trip within a datacenter  | ~500 µs | ~6 days                        |
| Read 1 MB from SSD              |    ~1 ms | ~12 days                       |
| Disk (HDD) seek                 |   ~10 ms | ~4 months                      |
| Round trip across the ocean     |  ~150 ms | ~5 years                       |

**The lesson in one line:** *a network call within a datacenter is thousands of
times slower than reading RAM, and a call across the world is millions of times
slower.*

This is *the* reason system design exists. Every architectural choice —
caching, colocating services, batching, message buses — is fundamentally about
**avoiding slow operations** or **doing them fewer times**.

Practical consequences you'll see in Tazama:

- **Redis (in-memory) is used for hot lookups** because RAM ≈ 100ns vs a full
  DB query. (Module 3.4)
- **Services are colocated** (same cluster/datacenter) so hops are ~500µs, not
  150ms.
- **NATS keeps messages small** so serialization and transfer stay cheap.

## Little's Law — the one formula worth knowing

$$
L = \lambda \times W
$$

- **L** = average number of requests *in the system at once* (concurrency)
- **λ** (lambda) = arrival rate (throughput, req/s)
- **W** = average time a request spends in the system (latency, s)

Rearranged: **throughput = concurrency / latency**.

Why this is powerful: it tells you that if each request takes **W = 50ms** and
you want **λ = 3,000 req/s**, you need **L = 3000 × 0.05 = 150** requests
being processed *simultaneously*. That immediately tells you how many workers /
threads / service replicas you roughly need. This one formula connects "how
fast is one request" to "how many machines do I need."

> **Try it:** If a Tazama rule processor handles one message in 20ms, how many
> concurrent messages must be in flight to sustain 3,000 tx/s? (Answer: 60.)
> Now you know roughly how much you'd need to scale that processor.

## Scalability: vertical vs horizontal

Two ways to handle more load:

- **Vertical scaling** ("scale up"): a bigger machine — more CPU/RAM. Simple,
  but there's a ceiling and it's expensive, and it's a single point of failure.
- **Horizontal scaling** ("scale out"): *more* machines running copies. No hard
  ceiling, survives one machine dying — but only works if your service can run
  as **many independent copies** (i.e., it's **stateless**, see [1.4](1.4-state-the-hard-problem.md)).

Tazama's rule processors are designed to scale **horizontally**: run N copies,
each pulls messages off NATS, all sharing the load. This is only possible
*because* they're stateless request-handlers that keep their state in shared
databases, not in local memory. **The messaging + stateless-worker pattern is
the single most important scaling pattern in the whole system** — hold that
thought for Module 2 and 3.
