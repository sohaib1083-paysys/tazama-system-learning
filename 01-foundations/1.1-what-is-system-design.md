# 1.1 — What "system design" even means

## The one-sentence definition

> **System design is the practice of deciding how to split a problem across
> multiple moving parts, and how those parts talk, so that the whole thing
> meets its goals — speed, cost, reliability — even when parts fail.**

Coding is "make this function correct." System design is "make these 12
services, 3 databases, and a message bus behave like one correct, fast,
survivable product." It's a different skill, and it's mostly about **tradeoffs**,
not right answers.

---

## First principle: a computer is fast, but a *system* is a network of slow links

A single CPU does billions of things per second. The moment you have **two
machines**, everything changes:

- They can't share memory. They must **send messages** over a network.
- The network is ~**a million times slower** than local memory, and it can
  **lose or delay** your message.
- The other machine can **crash** halfway through your request.
- Two machines can try to change the same thing **at the same time**.

Almost every hard thing in system design comes from those four facts. Keep them
in your head. When something in a distributed system feels needlessly
complicated, it's usually paying rent on one of those four problems.

---

## Why not just one big program?

You *could* write Tazama as a single program on one giant machine. It would be
simpler to reason about. So why is Tazama instead ~10 separate services talking
over a message bus? Because a single program has hard limits:

| Limitation of "one big program" | What splitting buys you |
|---|---|
| One machine has a ceiling (CPU/RAM). | **Scale**: run 20 copies of the slow part only. |
| One bug crashes everything. | **Isolation**: one rule crashing doesn't stop the pipeline. |
| Deploy = restart the whole thing. | **Independent deploys**: ship one rule without touching the API. |
| Everyone edits one codebase. | **Team autonomy**: teams own services. |
| Written in one language. | **Right tool per job.** |

This is the core justification for **microservices** and it's exactly why
Tazama looks the way it does. But — and this is the senior insight — **you pay
for every one of those benefits** with network calls, partial failure, and
operational complexity. Splitting is not free. A lot of "microservices" horror
stories are teams that paid the cost without needing the benefit.

> **Senior heuristic:** Split a service out when you have a *real* reason
> (independent scaling, isolation, team boundaries) — not because
> "microservices are modern." The default should be "as few moving parts as the
> problem allows."

Tazama has a real reason: the rule processors are the part that needs to scale
to **3,000+ transactions/second**, and there can be *many different rules*
maintained somewhat independently. So splitting the rules out from the API is
justified. (You'll see this concretely in Module 2.)

## The four questions you ask about any system

When you look at *any* system — designing one, or trying to understand
Tazama — ask these in order:

1. **What comes in, what goes out?** (The contract at the edges.)
   → For Tazama: an ISO 20022 transaction comes in over HTTP; an alert /
   decision goes out to a case management system.

2. **What's the flow?** (The ordered path a request takes through the parts.)
   → TMS → Event Director → Rule Processors → Typology Processor → TADProc.
   (We trace this in [2.2](../02-tazama-architecture/2.2-transaction-journey.md).)

3. **Where does state live?** (Databases, caches — the memory of the system.)
   → ArangoDB for transactions/history, Redis for fast lookups.

4. **What happens when a part fails?** (Because it *will*.)
   → This is [1.5](1.5-design-for-failure.md), and it's what Tazama's design
   principles call out explicitly.

If you can answer those four about a system, you *understand* it. Most of this
curriculum is teaching you to answer them well.

## The vocabulary you'll actually use

You don't need buzzwords, but these five you'll hear constantly. Plain
definitions:

- **Latency** — how long *one* request takes. (Lesson 1.2)
- **Throughput** — how many requests per second the system handles. (1.2)
- **Scalability** — can it handle more load by adding machines? (1.2)
- **Availability** — what fraction of the time is it up? (1.5, 6.4)
- **Consistency** — do all parts agree on the current data? (1.4)

Note that these often **fight each other**. Making something more consistent
often makes it slower. Making it more available often means tolerating stale
data. **A system designer's job is choosing which to sacrifice for the goal at
hand** — a fraud engine that must block a transaction in real time makes very
different choices than a monthly analytics report.
