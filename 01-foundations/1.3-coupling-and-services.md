# 1.3 — Coupling, cohesion & why we split into services

## Two words that decide whether a system is maintainable

- **Cohesion** — how much the things *inside* one module belong together. High
  cohesion = a service does *one job* and does it well.
- **Coupling** — how much one module *depends on the internals of another*. Low
  coupling = you can change one without breaking the other.

The entire goal of good design is: **high cohesion, low coupling.** Say it
until it's boring, because almost every "this codebase is a nightmare" story is
really "low cohesion (everything does everything) and high coupling (nothing
can change without breaking five other things)."

---

## Why Tazama is many services, and how it keeps coupling low

Tazama could be one program. Instead it's a chain of small services:

```
TMS/Event-Monitoring  →  Event Director  →  Rule Executers (×N)  →  Typology Processor  →  TADProc  →  Case Management
```

Each has **one job** (high cohesion):

| Service | Its one job |
|---|---|
| **Event Monitoring / TMS** | Accept transactions over HTTP, validate, normalize, persist. |
| **Event Director** | Look up which rules apply, fan the transaction out to them. |
| **Rule Executer** | Run *one* rule, produce a rule result. |
| **Typology Processor** | Combine rule results into typology scores. |
| **TADProc** | Aggregate + decide (block / allow / alert). |
| **Case Management** | Let humans investigate the alerts. |

Now the crucial part — **how do they stay loosely coupled?** They don't call
each other's functions. They don't share a database schema in-process. They
communicate by **dropping messages on a message bus (NATS)** addressed to a
**subject** (a string like `event-director` or `sub-rule-901@1.0.0`).

This is the key idea, so slow down:

> The Event Director does **not** know which machine a rule runs on, how many
> copies exist, or even whether it's up right now. It publishes a message to the
> subject `sub-rule-<ruleId>` and moves on. Whatever is subscribed to that
> subject picks it up. **The subject string is the contract. Everything else is
> hidden.**

That is **loose coupling via a message bus**, and it's the single most
important structural decision in Tazama. Consequences:

- You can deploy a **new version of a rule** without touching the Event Director
  — same subject, new code behind it.
- You can run **20 copies** of a hot rule; they all subscribe to the same
  subject and share the load. The publisher is oblivious.
- If a rule is **down**, the message waits on the bus (with JetStream
  persistence) instead of the whole request failing.

Compare to the tightly-coupled alternative — the Event Director makes a **direct
HTTP call** to `http://rule-901:3000/execute`. Now it must know the rule's
address, handle it being down, handle it being slow, and you can't add a copy
without a load balancer in between. Every one of those is a coupling you've
taken on. The message bus removes them.

## The contract is the interface — and interfaces should be *narrow*

When services talk over messages, **the message shape is the API**. Tazama
formalizes this: shared TypeScript interfaces (like `Pacs002`, `NetworkMap`,
`RuleResult`, `DataCache`) live in a shared library (`frms-coe-lib`) that every
service imports. That shared library *is* the set of contracts.

Senior insight about shared contracts — there's a tension:

- A shared library of types means everyone agrees on message shapes. 
- But it also means the shared library is now a thing **all services couple
  to**. Change `RuleResult` carelessly and you can break every service at once.

So the rule is: **shared contracts should change rarely and additively.** Add
optional fields; don't rename or repurpose existing ones. This is versioning
discipline, and you'll see it in Tazama's subjects: `pub-rule-<name>@<version>`
— the **version is in the subject itself**, so a v2 rule can coexist with v1.
That's how you evolve a contract without a flag-day where everything must change
at once.

## Conway's Law (why org charts leak into architecture)

> "Organizations design systems that mirror their own communication structure."
> — Melvin Conway

If three teams build a system, you'll get three services with awkward seams
where the teams don't talk. This isn't a bug — it's physics of organizations.
Senior engineers use it *deliberately*: draw service boundaries where team
boundaries are, so each team owns a service end-to-end. Tazama's "one rule = one
deployable unit" maps naturally to "one person/team can own a rule."

---

## The cost side (don't skip this)

Splitting into services buys the benefits above, but the bill includes:

- **Network calls** where you used to have function calls (slower, can fail).
- **Debugging across services** — a bug's cause and symptom are now in different
  processes. (This is why observability, Module 6.2, becomes essential.)
- **Operational overhead** — more things to deploy, monitor, secure.
- **Eventual consistency** — data is spread across services and isn't instantly
  in sync everywhere.

> **Senior heuristic restated:** the number of services should be the *minimum*
> that gives you the isolation/scaling/ownership you actually need. Tazama's
> split is justified by real scaling needs (rules must scale independently to
> thousands of tx/s) — not fashion.
