# 1.4 — Statefulness, and why it's the hardest problem

## Stateless vs stateful — the distinction that unlocks scaling

- A **stateless** service remembers *nothing* between requests. Every request
  carries everything it needs, or the service fetches what it needs from a
  shared store. Restart it, run 50 copies — no difference.
- A **stateful** service keeps important data *in its own memory or disk*.
  Restart it and you lose something. Run 50 copies and they disagree.

Here's why this is the master key to scaling:

> **You can horizontally scale a stateless service trivially** — just run more
> copies behind the same subject/load balancer. **You cannot trivially scale a
> stateful one**, because the copies would each have different state.

So the winning move, used everywhere including Tazama, is:

**Push all the state *out* of your services and *into* dedicated data stores.
Keep the services stateless. Scale the stateless services freely. Scale the
(harder) stateful stores carefully and rarely.**

---

## How Tazama applies this

Look at Tazama's rule executers. Each one:

1. Receives a message (transaction + network map) — everything it needs is *in
   the message*.
2. Fetches any extra data it needs (rule config, transaction history) from
   **shared stores** — PostgreSQL and Redis/Valkey.
3. Produces a result message.
4. Remembers **nothing** afterward.

That's why you can run N copies of a rule executer subscribed to the same
subject — they're stateless workers. **The state lives in PostgreSQL (durable
history/config) and Redis/Valkey (fast shared cache), not inside the
processors.** This is *the* reason Tazama can scale rule processing to thousands
of transactions per second.

The stores themselves are the stateful, "hard" part — which is exactly why
Tazama's team spends effort benchmarking ArangoDB/PostgreSQL clustering (you saw
those docs in [1.2](1.2-latency-throughput-numbers.md)). **The hard scaling
problems get concentrated into the data layer, where you can afford to solve
them carefully, instead of being smeared across every service.**

## Why state is genuinely hard: the CAP theorem

When state is spread across multiple machines (for scale or survival), you hit a
law of nature. Suppose two copies of your database on two machines. A network
problem cuts them off from each other (a **partition** — the "P"). A write
arrives. You have exactly two choices:

- **Accept the write** on the reachable copy — now the two copies **disagree**
  (you sacrificed **Consistency**), but you stayed up (**Availability**).
- **Refuse the write** until the copies can talk again — you stayed
  **Consistent**, but you were **unavailable** for that write.

**CAP theorem:** when a partition happens (and at scale, it *will*), you must
choose between **C**onsistency and **A**vailability. You cannot have both during
a partition. There is no clever engineering around it; it's a proof.

The senior skill is knowing **which to pick per use case**:

| Data | Pick | Why |
|---|---|---|
| Bank account balance | **Consistency** | Never let two ATMs both dispense the last $100. |
| "Number of likes" | **Availability** | Nobody's harmed if the count is briefly stale. |
| Fraud decision to **block** a transaction | Consistency-leaning | A wrong "allow" moves real money. |
| A cached network-map lookup | Availability-leaning | Slightly stale config is tolerable; being down isn't. |

Notice Tazama itself lives on **both** sides: it caches the network map
aggressively in Redis/node-cache (favoring speed/availability for config reads)
*but* the money-movement decision path is treated with much more care. Different
data, different choice. **That nuance — not "we chose CP" or "we chose AP" as a
whole-system slogan — is the real skill.**

## Idempotency: the survival tool for stateful operations

In a distributed system, messages get **retried** (the network dropped the ack,
so the sender sends again). If "process this transaction" runs **twice**, do you
create two records? Charge twice? Score twice?

An operation is **idempotent** if doing it twice has the same effect as doing it
once. Design your handlers to be idempotent — e.g., key records by a unique
transaction ID so a duplicate insert is a no-op rather than a double. This is
why Tazama messages carry stable identifiers (like an end-to-end transaction ID)
— they let downstream stages **dedupe** and stay correct under retries.

> **Rule of thumb:** in a system with a message bus and retries (i.e. any
> serious distributed system), assume **every message can be delivered more than
> once**, and make your processing idempotent. "At-least-once delivery" is the
> common guarantee; "exactly-once" is mostly a marketing word — you achieve its
> *effect* through idempotency.
